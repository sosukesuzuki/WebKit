§1問題：o.x はなぜ遅いか

インラインキャッシュは「同じ場所で実行されるプロパティアクセスは、たいてい同じ形のオブジェクトを相手にする」という経験則を、実行時に発見して機械語やデータ構造へ焼き付ける仕組みである。まず、それが無いと何が起きるかを確認する。

1.1仕様どおりに o.x を評価すると

ECMAScript の o.x は [[Get]] 内部メソッドの呼び出しであり、素直に実装すると次のような仕事になる。

  1. o がオブジェクトかどうかを調べる（プリミティブなら対応するプロトタイプへ迂回する）。
  2. o 自身のプロパティ表から "x" を探す（ハッシュ表の検索）。
  3. 見つからなければ o.[[Prototype]] をたどって 2 を繰り返す。チェーンの末尾まで無ければ undefined。
  4. 見つかったものがデータプロパティなら値を返す。アクセサなら getter を this = o で呼ぶ。Proxy や DOM オブジェクトのような exotic object なら、そのオブジェクト固有の [[Get]] を呼ぶ。

JSC でこの「一般の道」に相当するのが JSValue::get → JSObject::getPropertySlot → getOwnPropertySlot の連鎖であり、結果は PropertySlot という構造体に詰められて返る。1 回のアクセスにハッシュ計算・仮想関数呼び出し・ループが伴い、o.x 1 個につき数十〜数百命令かかる。JavaScript プログラムはプロパティアクセスの塊なので、これがそのまま実行速度を決めてしまう。

1.2観察：アクセスサイトはたいてい単相である

一方で、ソースコード上の特定の 1 箇所（アクセスサイト）に注目すると、そこを通るオブジェクトの「形」は驚くほど偏っている。function area(r) { return r.w * r.h; } の r.w には、ほとんどの場合同じコンストラクタで作られた、同じレイアウトのオブジェクトが来る。この性質は Smalltalk-80 の実装（Deutsch & Schiffman, 1984）でメソッド呼び出しの高速化に使われたのが最初で、Self（Hölzle ら, 1991）が「複数の形を同時に覚える」多相インラインキャッシュ（PIC）へ拡張した。JSC の IC はこの系譜の直系であり、用語（monomorphic / polymorphic / megamorphic）もそのまま受け継いでいる。

定義 1.1

インラインキャッシュとは、あるアクセスサイトについて「直前までに観測したオブジェクトの形」と「その形に対する答え（値の格納位置など）」の組を、そのサイト専用の記憶域に保持しておき、次回以降は形の一致確認だけで一般の道を省略する仕組みである。「インライン」の語源は、記憶域が呼び出し元の機械語の中に埋め込まれていたことによる。JSC では機械語に埋め込む形態（§9）と、機械語の外のデータ構造に置く形態（§4, §8）の両方が使われるが、どちらも IC と呼ぶ。

したがって IC には、どの実装にも共通する 3 つの部品がある。

  • ガード（guard）—「今来たオブジェクトは覚えている形と同じか」を判定する安価な検査。JSC ではほぼ常に StructureID の 32bit 比較 1 回である（§2）。
  • ペイロード—ガードが通ったときに実行する、答えそのもの（「オフセット 3 のスロットを読む」「このプロトタイプオブジェクトのオフセット 1 を読む」「この getter を呼ぶ」）。
  • スローパス（slow path）—ガードが外れたときに呼ぶ一般の道。ここで正しい答えを計算すると同時に、次回のために IC を育てる（§6）。

加えて JSC の IC には、他の処理系より強く意識されている第 4 の部品がある。無効化（invalidation）である。ペイロードが「プロトタイプ上の x は存在しない」といった他のオブジェクトに関する仮定を含む場合、その仮定が崩れた瞬間にキャッシュを捨てなければならない。JSC はこれを watchpoint という仕組みで行う（§11）。

1.3本章の読み方

本章では、キャッシュされる対象として主に get_by_id（o.x）と put_by_id（o.x = v）を追う。JSC の IC 基盤は in、delete、instanceof、o[k]（by-val）、private field、private brand まで同じ枠組みで扱うが（AccessType は 30 種類ある。§5）、仕組みは get_by_id を理解すれば残りは差分で済む。

各節の末尾には「ソース」ボックスで読むべきファイルと行を示す。IC は JSC の中でも特に変化の速い部分であり、たとえばこのリビジョンでは長年 StructureStubInfo と呼ばれていたクラスが PropertyInlineCache に改名され、Baseline と DFG の IC が「Handler IC」と呼ばれる新方式へ全面移行している。古い資料と名前が食い違ったら、本章の名前のほうが新しいと考えてよい。

§2土台：Structure と PropertyOffset

IC のガードが「32bit 比較 1 回」で済み、ペイロードが「固定オフセットのロード 1 回」で済むのは、JSC のオブジェクト表現がそのように設計されているからである。本節では IC が依存するランタイム構造だけを、IC の視点から必要最小限に整理する。

2.1Structure（隠れクラス）

JSC のオブジェクトは、プロパティ名からスロット番号への対応表を自分では持たない。その対応表とプロトタイプ・型情報・各種フラグをまとめた Structure というセルを別に持ち、同じ順序で同じプロパティを追加されたオブジェクトは同じ Structure を共有する。他処理系でいう hidden class / shape / map と同じ概念である。

プロパティを追加すると、オブジェクトは「元の Structure に x を足したもの」を表す別の Structure へ遷移（transition）する。遷移先は元の Structure の遷移表（m_transitionTable）に記憶されるので、2 個目以降のオブジェクトは同じ経路をたどって同じ Structure に到達する。runtime/Structure.cpp:562-626

定義 2.1

IC における「オブジェクトの形」とは、そのオブジェクトが現在指している Structure のことである。Structure が同じなら、（a）どのプロパティがどのオフセットにあるか、（b）プロトタイプが何か（2.5 の poly proto を除く）、（c）getter/setter や読み取り専用属性の有無、（d）C++ 側で [[Get]] をオーバーライドしているかどうか、がすべて同じであることが保証される。IC はこの保証の上に成り立つ。

2.2StructureID：ガードを 32bit 比較にする仕掛け

すべての JS セルは先頭 4 バイトに StructureID を持つ。runtime/JSCell.h:293-302 これは uint32_t であり、その正体は Structure のアドレスの下位 32bit である。runtime/StructureID.h:71-97 Structure は専用の、サイズにアラインされた予約領域にだけ確保されるので、上位 32bit は VM 内で常に一定（g_jscConfig.structureIDBase）になり、下位 32bit だけで一意に識別できる。heap/StructureAlignedMemoryAllocator.cpp:106-124

その結果、IC のガードは次の 1 命令（＋分岐）で済む。

; base レジスタが指すセルの先頭 4 バイトと、覚えておいた ID を比較する
cmp   dword ptr [base + 0], 0x1234abc0      ; JSCell::structureIDOffset() == 0
jne   miss

ID の値 0 は「なし」を意味し、リンク直後の LLInt キャッシュが「必ず外れる」状態を表すのに使われる（§4）。最下位ビットは、butterfly を差し替えている最中であることを並行 GC に知らせる「nuke」ビットとして一時的に立てられる。runtime/StructureID.h:39-51

2.3PropertyOffset と 2 種類の格納場所

プロパティの値は 2 箇所のどちらかに置かれる。オブジェクトセル本体の末尾に確保された inline storage と、セルの 8 バイト目にあるポインタ（butterfly）が指す外部領域の out-of-line storage である。PropertyOffset（実体は int）はこの両方を 1 本の番号で表す。

ここで重要なのは、Structure が決まればオフセットも inline/out-of-line の別も決まるということである（inline 容量は Structure の m_inlineCapacity に含まれ、番号付けにも織り込まれている runtime/PropertyOffset.h:136-144）。ゆえに IC のペイロードは「Structure S のとき、オフセット o をロードせよ」という 1 組の定数だけで完全に記述できる。

プロパティ追加で out-of-line 容量が足りなくなると butterfly の再確保が必要になる。容量は 0 → 4 → 8 → 16 … と段階的にしか増えないのでruntime/Structure.h:499-517、遷移をキャッシュする put IC は「旧 Structure と新 Structure の容量が同じか」で再確保の要否を静的に判定できる（§7, §8）。

2.4Dictionary：形の保証が崩れるオブジェクト

遷移が長くなりすぎたり（1 本の遷移列で 128 回、put_by_id 文脈では 512 回 runtime/Structure.h:250-258）、プロパティが削除されたりすると、Structure は dictionary モードに切り替わる。dictionary Structure はオブジェクトと 1 対 1 に対応し、以後プロパティを追加してもStructure を遷移させずにその場で書き換える。runtime/StructureInlines.h:397-447 つまり定義 2.1 の保証（b）（c）が「Structure が同じでも中身が変わりうる」という形で破れる。

dictionary には 2 段階ある。

  • cacheable dictionary：追加はその場で行うが、削除はまだ遷移で表す。StructureID はそのオブジェクト固有なので、そのオブジェクト自身のプロパティへの自己アクセス（self access）は依然キャッシュできる。ただし「プロトタイプチェーン上に x は無い」といった不在の事実は、その場での追加で黙って覆るのでキャッシュできない。bytecode/PropertyCondition.cpp:137-142
  • uncacheable dictionary：削除もその場で行い、オフセットの再利用が起きるので、何もキャッシュできない。propertyAccessesAreCacheable() が偽を返す。runtime/Structure.h:332-337

IC の C++ 側は dictionary に出会うと、いきなり諦めるのではなく、まず flatten（辞書を通常の Structure に戻し、オフセットを詰め直す）を 1 回だけ試み、次回のアクセスで改めてキャッシュを狙う。flatten はStructureID を変えずにオフセットを付け替えるため、flatten した瞬間のオフセットではキャッシュできず「次回に持ち越す」必要があるのが、この RetryCacheLater の理由である。2 度目（hasBeenFlattenedBefore()）は諦める。bytecode/Repatch.cpp:340-360, runtime/Structure.cpp:1025-1111

2.5Poly proto：プロトタイプが Structure に含まれない場合

通常の Structure は m_prototype にプロトタイプを保持しており（mono proto）、Structure 一致 ⇒ プロトタイプ一致が成り立つ。しかし、同じクラス定義から異なるレルムやクロージャごとに別々の prototype オブジェクトが生じると、Structure がプロトタイプごとに分裂して IC が無駄に多相化する。JSC はこれを検出すると（Structure::shouldConvertToPolyProto runtime/StructureInlines.h:487-531）、以後そのコンストラクタが作るオブジェクトを poly proto Structure に切り替える。poly proto Structure は m_prototype を空にし、代わりに各オブジェクトの inline slot 0（knownPolyProtoOffset）にプロトタイプを格納する。runtime/Structure.cpp:409-426

IC から見ると、poly proto の場合は「Structure を見ただけではプロトタイプが分からない」ので、プロトタイプチェーンをたどるアクセスでは各段のオブジェクトを実際にロードして Structure を確認する必要がある。このために PolyProtoAccessChain（各段の期待 StructureID の配列）という別のペイロード表現が用意されている（§6.4）。IC が 2 つ目のケースを追加しようとした際に「これは poly proto に転換すべき組だ」と気付くと、IC 自身をリセットして watchpoint を発火させる ResetStubAndFireWatchpoints という特殊な結果を返す。bytecode/PropertyInlineCache.cpp:117-157

2.6Watchpoint：仮定が崩れたことを知る仕組み

最後に、§11 で本格的に扱う watchpoint を導入しておく。WatchpointSet は ClearWatchpoint → IsWatched → IsInvalidated と一方向に進む 3 状態の小さなオブジェクトで、Watchpoint（コールバック）を登録しておくと、対応する事象が起きて fireAll されたときに呼び出される。bytecode/Watchpoint.h:152-282 IC にとって特に重要なのは、各 Structure が 1 つずつ持つ遷移 watchpoint set（m_transitionWatchpointSet）である。ある Structure から別の Structure へ遷移が起きると、元の Structure のこの set が発火する。IC が「プロトタイプ P の Structure は S_P のままである」という仮定に依存するとき、S_P の遷移 watchpoint set に自分を登録しておけば、P にプロパティが足されたり削られたりした瞬間に通知を受けられる。

この set は生成時から IsWatched 状態で作られる。runtime/Structure.cpp:339 したがって誰も監視していなくても、一度でも遷移元になった Structure の set は IsInvalidated になっており、これが「この Structure はもう遷移木の葉ではない」という印として使われる。葉でない Structure（＝そこから先へ進んだオブジェクトが既にいる）に監視を仕掛けても即座に無効なので、IC はその条件を watchpoint ではなく明示的な比較で守ることになる（§11.1）。

§3全体地図：階層ごとの IC の形

JSC には実行階層（tier）が 4 つあり、IC の「記憶域をどこに置くか」は階層ごとに異なる。一方で「何をキャッシュするか」を決める C++ 側の判断ロジックは JIT 階層の間で完全に共有されている。この分担を先に頭に入れておくと、以降の節が読みやすい。

3.1なぜ Baseline／DFG と FTL で方式が違うのか

PropertyInlineCache.h の冒頭コメントがこの設計判断を端的に述べている。bytecode/PropertyInlineCache.h:97-119 要約すると次のとおりである。

  • Repatching IC は、観測したケース集合にぴったり合わせた専用コードを生成でき、ケースが増えれば StructureID の二分探索（binary switch）で分岐できるので、実行スループットは最も高い。反面、実行時に機械語を書き換えるコストが大きい（命令キャッシュのフラッシュ、プラットフォームによっては書き込み権限の切り替え）うえ、ケースが 1 つ増えるたびに stub 全体を作り直す。
  • Handler IC は、ケースを 1 つ足すのに連結リストへノードを 1 個つなぐだけでよく、機械語も大半が VM 全体で共有された thunk なので、生成コストがきわめて低い。反面、実行時には間接分岐を 1 段以上余計にたどる。

Baseline と DFG のコードは「まだプロファイル中」で、コードが捨てられ（jettison）作り直されることも多い。ここでは生成コストの安さが効く。FTL に到達したコードは十分に熱く、形も定常状態に達している見込みが高いので、書き換えコストを払ってでも実行速度を取る。useHandlerICInFTL というオプションがあり FTL でも Handler IC を使う作業が進行中だが、このリビジョンでは「未完成」として強制的に無効化されている。runtime/Options.cpp:839

§4LLInt のメタデータキャッシュ

最も単純な IC はインタプリタにある。JIT 側の重厚な基盤（§5 以降）は一切使わず、命令ごとのメタデータに structureID とオフセットを書き込むだけである。しかし「ガード・ペイロード・スローパス・無効化」の 4 部品はすべて揃っており、IC の骨格を学ぶ教材として最適である。

4.3スローパス：キャッシュを書き込む

ガードが外れると llint_slow_path_get_by_id → performLLIntGetByID に落ちる。llint/LLIntSlowPaths.cpp:851-915 ここではまず一般の道 baseValue.get() で正しい答えを求め、副産物として得られた PropertySlot を見てキャッシュ可否を決める。判定は次の 3 分岐だけである。

  1. 自分自身の値プロパティだった（slot.isValue() && slot.slotBase() == baseValue）：Default モードにして structureID とオフセットを書く。ただし Structure が propertyAccessesAreCacheable()（§2.4）を満たし、impure property（DOM の名前付きプロパティなど、C++ 側が黙って生やしうるプロパティ）を持たない型であること。同時に hitCountForLLIntCaching を 0 にし、以後このサイトではプロトタイプキャッシュを二度と試みない。
  2. プロトタイプ上の値プロパティだった：hitCountForLLIntCaching（初期値は Options::prototypeHitCountForLLIntCaching() = 2）を減らし、0 になった時点で初めて setupGetByIdPrototypeCache を呼ぶ。プロトタイプキャッシュは watchpoint の設置というコストを伴うので、2 回観測するまで様子を見るわけである。
  3. JSArray の length だった：ArrayLength モードにする（length は cacheable な slot として返ってこないので、別枠で判定している）。

getter、custom accessor、文字列の length、そして不在（miss）は LLInt ではキャッシュされない。これらは Baseline 以降の仕事である。

4.4プロトタイプキャッシュと adaptive watchpoint

setupGetByIdPrototypeCache llint/LLIntSlowPaths.cpp:794-849 は、JIT 側と同じ generateConditionsForPrototypePropertyHit（§6.4）を呼んで「途中のプロトタイプには x が無い（Absence）」「保持元には x がオフセット o にある（Presence）」という条件の集合を得る。そして条件 1 つにつき 1 個の LLIntPrototypeLoadAdaptiveStructureWatchpoint を、その条件が言及するオブジェクトの現在の Structure の遷移 watchpoint set に登録し、CodeBlock::m_llintGetByIdWatchpointMap（キーは (base の StructureID, 命令位置)）に保管する。最後にメタデータを ProtoLoad に切り替える。

この watchpoint が発火したとき——つまりチェーン上のどれかのオブジェクトの Structure が変わったとき——の振る舞いが「adaptive」の名の由来である。bytecode/LLIntPrototypeLoadAdaptiveStructureWatchpoint.cpp:71-134

  • 条件を新しい Structure に対して評価し直し、まだ成り立っていれば（例：プロトタイプに無関係なプロパティ y が足されただけ）、新しい Structure の遷移 watchpoint set に自分を登録し直して終わり。キャッシュは生き残る。
  • 成り立たなくなっていれば、メタデータを Default（structureID = 0）に戻す。hitCount は 0 のままなので、このサイトは以後、自己アクセスとしてなら再キャッシュされるが、プロトタイプキャッシュには二度と入らない。

「仮定が形式的に破れたか」ではなく「仮定の内容が破れたか」で無効化を判断するこの adaptive 方式は、JIT の IC（§11）でも DFG の watchpoint でも同じ形で使われる。プロトタイプオブジェクトはプログラム起動時に大量のメソッドを次々と生やされるのが普通なので、これが無いとキャッシュはほとんど生き残れない。

4.5put_by_id：遷移のキャッシュ

put_by_id のメタデータは oldStructureID / offset / newStructureID / structureChain の 4 フィールドである。bytecode/BytecodeList.rb:294-306 newStructureID == 0 なら「既存プロパティの上書き（replace）」、非 0 なら「プロパティ追加による遷移（transition）」を表す。ファストパス llint/LowLevelInterpreter64.asm:1745-1815 の遷移側は次のことを行う。

  1. base の structureID が oldStructureID に一致することを確認する。
  2. structureChain が設定されていれば（put_by_id が direct でない、すなわち通常の代入なら）、現在のプロトタイプチェーンを 1 段ずつたどり、各段のオブジェクトの structureID が記憶しておいた StructureChain の対応要素と一致することを確認する。これは「チェーン上のどこにも setter や読み取り専用の x が現れていない」ことの検査であり、LLInt は watchpoint を使う代わりに毎回歩いて確かめる。
  3. base の先頭 4 バイトに newStructureID を書き込む。これが Structure 遷移の実体である。あとは値をオフセットに格納し、write barrier を実行する。

5.4カウンタ：育てすぎないための抑制

IC を育てる操作（ケースの追加、stub の再生成）はそれ自体が高価であり、形が絶えず変わるサイトで毎回行うと逆に遅くなる。considerRepatchingCacheImpl() bytecode/PropertyInlineCache.h:237-331 は、スローパスが「今回 IC を育ててよいか」を問い合わせる関門で、以下の 3 段階の抑制を行う。すべてのスローパス operation は、まずこの関門を通ってから Repatch.cpp に進む。

  1. countdown（初期値 1）— 0 のときだけ先へ進み、そうでなければ減らして「今回は何もしない」。初期値が 1 なので、JIT の IC は最初のスローパス通過ではキャッシュせず、2 回目で初めて育つ。stub 内で「キャッシュ不能な理由で失敗した」経路（m_failAndIgnore）はこの値を +1 して、次のスローパスに育てさせないようにする。bytecode/InlineCacheCompiler.cpp:8050-8060
  2. クールダウン— 育てるたびに repatchCount を増やし、repatchCountForCoolDown（既定 8）を超えたら countdown に initialCoolDownCount（既定 20）<< numberOfCoolDowns を設定して、しばらく（回を追うごとに指数的に長く）育てるのをやめる。
  3. バッファリングと重複除去— bufferingCountdown（既定 6）が残っている間は、既に m_bufferedStructures に載っている Structure については「何もしない」を返し、新しい Structure のときだけ先へ進む。Repatching IC ではさらに、この期間中に追加されたケースは PolymorphicAccess の一覧に溜めるだけでコード生成せず、bufferingCountdown が 0 になった時点でまとめて 1 回だけ再生成する（§9.3）。

6.2tryCacheGetBy：キャッシュ可能性の判定木

tryCacheGetBy bytecode/Repatch.cpp:471-744 は約 270 行の関数で、IC 基盤の「知識」の大半がここに集約されている。判定は概ね次の順序で行われる。

§8Handler IC（Baseline／DFG）

Handler IC は、このリビジョンの JSC で Baseline と DFG のすべてのプロパティ IC が採用している方式である。設計の核心は「コールサイトの機械語は一切書き換えず、IC の状態をすべてデータ構造（InlineCacheHandler の連結リスト）に置く」ことにある。その帰結として、handler の機械語を VM 全体で共有できるようになり、ケース追加のコストが劇的に下がった。

8.3単相の高速化：inline 検査への昇格

図 8.1 の一般経路は、単相のサイトに対しても「IC をロード → handler をロード → 間接 call → 比較 → ロード → ret」という手順を要し、Repatching IC の「比較 → ロード」より明らかに遅い。これを補うのが §8.1 の inline 検査と m_inlinedHandler である。

prependHandler() は、生成された handler の cacheType（GetByIdSelf／GetByIdPrototype／PutByIdReplace／InByIdSelf）がコンパイル時に予約した preconfiguredCacheType と一致し、かつまだ昇格枠が空いていれば、その handler をリストにつなぐ代わりに m_inlinedHandler に保持し、その structureID・オフセット・保持元を IC 自身のフィールド（m_inlineAccessBaseStructureID 等）に転記する。bytecode/PropertyInlineCache.cpp:828-863 コールサイトの inline 検査はこのフィールドを読むので、以後この形はリストに触れずに処理される。昇格枠は 1 つだけで、2 つ目以降のケースは通常どおりリストに入る。

ここで §4 と §5.3 の伏線が回収される。Baseline は LLInt のメタデータが ProtoLoad だったサイトの preconfiguredCacheType を GetByIdPrototype にしておくため、プロトタイプ上のメソッド呼び出し（obj.method() の method の読み出しという最も頻出のパターン）でも inline 検査が効く。DFG は GetByStatus::preferredCacheType() で同じ判断をする。

  2. stateless stub — ArrayLength や添字アクセスのように、ケースがデータを一切持たない種類（isStateless()）は、(サイトの種類, ケースの種類) をキーに SharedJITStubSet::m_statelessStubs で 1 度だけ生成・共有される。
  3. SharedJITStubSet — 上記に該当せず個別に生成する場合でも、生成前に AccessCase::canBeShared()（§7.4）で等価なケースの stub が既に無いかを VM 全体のハッシュ集合から探し、あればそれを使う。無ければ generateWithGuard() で生成し（このとき structureID や条件のオブジェクトは Repatching IC と同様に定数として焼き込まれる）、生成物を集合に登録する。bytecode/SharedJITStubSet.h 同じクラスの同じプロパティにアクセスするサイトはプログラム中に無数にあるので、これも高い確率で当たる。

共有の前提は、handler の機械語がサイト固有の情報（レジスタ割当、戻り先、例外ハンドラ）を含まないことである。レジスタは §5.1 の固定規約で、戻り先は ret で、スローパス関数は IC の m_slowOperation の間接呼び出しで、それぞれ抽象化されている。共有された 1 本の stub は複数の CodeBlock から参照されるため、所有者の集合（m_owners）を持ち、watchpoint による無効化も所有者ごとに配送される（§11.2）。

8.5呼び出しを伴う handler と prologue の設計

Handler IC の prologue（emitDataICPrologue bytecode/InlineCacheCompiler.cpp:1345-1404）には 2 つの設計上の工夫がある。

  • callFrameRegister を変更しない。 handler は呼び出し元の JS 関数のフレームの中で、その関数の一部として実行される。したがって例外の巻き戻し（unwind）や、operation が CallFrame* を必要とする場面で、handler 用の特別扱いが不要になる。
  • フレームの保存を遅延する。 ほとんどの handler は「比較してロードして戻る」だけの葉であり、リンクレジスタ／フレームポインタを退避する必要が無い。ARM64 では prologue は戻り番地に署名する（pacibsp）だけで、getter や C++ を実際に呼ぶことになった時点で初めて emitDataICPrepareForCall が LR/FP をプッシュする。x86_64 では call 命令が戻り番地をスタックに積んでしまうので、prologue で FP をプッシュして形を揃える。

JS の getter/setter を呼ぶケース（Getter／Setter）では、handler は InlineCacheHandlerWithJSCall となり、末尾に DataOnlyCallLinkInfo——すなわち呼び出し先を覚える別の IC（call IC）——を抱える。bytecode/InlineCacheHandler.h:179-192 stub は生きているレジスタをスタックに退避し、呼び出し先フレームを組み立て、この call IC 経由で getter を呼び、戻ってからレジスタを復元する。bytecode/InlineCacheCompiler.cpp:3399-3600 getter が例外を投げた場合に備えて専用の例外ハンドラも生成される。プロパティ IC の中に呼び出し IC が入れ子になっているわけで、DFG から見ると「getter のインライン展開」に必要な情報（どの関数が呼ばれたか）がここから得られる（§12）。

§9Repatching IC（FTL）

Repatching IC は、Smalltalk 以来の「機械語を書き換える」古典的なインラインキャッシュの直系であり、長らく JSC の全 JIT 階層で使われてきた方式である。現在は FTL 専用となった。この方式では IC の状態が「関数本体に埋め込まれた固定長スラブの中身」として表現され、状態遷移＝機械語の書き換えである。

9.1コンパイル時：スラブの確保

FTL は GetById ノードを B3 の patchpoint（B3 に「ここに後で自前の機械語を置く」と宣言する命令）として下降させ、その生成子の中で JITGetByIdGenerator::generateFastPath() を呼ぶ。ftl/FTLLowerDFGToB3.cpp:20543-20636, jit/JITInlineCacheGenerator.cpp:118-130 出力されるのは「スローパスへのジャンプ＋nop 詰め物」で、長さは InlineAccess::sizeForPropertyAccess()（x86_64 で 26 バイト、ARM64 で 40 バイト。length アクセス用はやや長い）に固定される。bytecode/InlineAccess.h:48-88 この長さは「structureID 比較 ＋ butterfly ロード ＋ 値ロード」が収まる大きさとして実測で決められており、InlineAccess::dumpCacheSizesAndCrash() という測定用関数が同居している。

リンク時に finalize() がスラブの先頭（startLocation）、直後（doneLocation）、スローパスの先頭（slowPathStartLocation）、スローパス内の call 命令（m_slowPathCallLocation）の 4 番地を IC に記録する。jit/JITInlineCacheGenerator.cpp:84-93 以後の書き換えはすべてこの 4 番地を基準に行われる。Handler IC と違い、レジスタは B3 が任意に割り当てたものをそのまま使い、その時点で生きているレジスタ集合が m_usedRegisters に記録される。IC のアドレスはスローパスの引数として即値で埋め込まれる。

9.2状態 1 → 2：InlineAccess

watchpoint や GC によるリセット（reset() → resetGetBy() → resetStubAsJumpInAccess()）は、スラブ先頭を slowPathStartLocation へのジャンプで上書きし、m_stub を捨て、スローパスの call を Optimize 版に戻す。bytecode/Repatch.cpp:2125-2130, bytecode/PropertyInlineCache.cpp:915-930 状態 1 からやり直しである。GiveUp／Megamorphic へのスローパスの差し替えは call 命令のターゲット書き換えだが、FTL のスローパス呼び出しは thunk を経由していることがあるため、それを考慮した ftlThunkAwareRepatchCall() が使われる。bytecode/Repatch.cpp:306-322

§11無効化と GC

IC は「過去に観測した事実」を覚えているだけなので、事実が変われば捨てなければならない。変わり方には 2 種類ある。プログラムがオブジェクトを書き換えて仮定が崩れる場合と、GC によって参照先が消える場合である。前者は watchpoint、後者は弱参照と GC 終了時の点検で扱う。どちらも最終的に PropertyInlineCache::reset() に合流する。

11.1条件を「監視する」か「検査する」か

§6.4 で作った条件集合は、コード生成時（Handler IC なら compileOneAccessCaseHandler、Repatching IC なら compile）に collectConditions() によって 2 群に振り分けられる。bytecode/InlineCacheCompiler.cpp:3140-3164

  • 監視できる条件（isWatchableAssumingImpurePropertyWatchpoint() が真）— 対象オブジェクトの Structure がまだ「遷移木の葉」であり（§2.6）、その遷移 watchpoint set が有効なもの。これらは機械語には現れず、代わりに watchpoint が登録される。ガードのコストはゼロである。
  • 検査するしかない条件— 対象の Structure から既に他へ遷移したオブジェクトが存在するなど、watchpoint がすぐ発火してしまう場合。stub の中に「そのオブジェクト（定数）の structureID が期待値か」という比較が明示的に出力される。:3166-3182 Handler IC では、この群が 1 つでもあると事前コンパイル済み thunk が使えず、個別生成に落ちる（§8.4）。

典型的なプログラムでは、プロトタイプオブジェクトは起動時にメソッドを生やし終えたあと安定するので、その最終 Structure は葉であり、ほとんどの条件は監視群に入る。結果として、プロトタイプ上のメソッド読み出しの IC は「base の structureID 比較 1 回 ＋ 保持元からのロード」だけの機械語になる。

11.2watchpoint の 2 段構造

1 段目の watchpoint が発火時に条件を再評価して登録し直す挙動（adaptive）は §4.4 で見たものと同じである。bytecode/PropertyInlineCacheClearingWatchpoint.cpp:61-79 WatchpointSet::fireAll の実装は、各 watchpoint をリストから外してから呼び出すので、呼び出された watchpoint が別の set（新しい Structure のもの）に自分を登録し直せる。bytecode/Watchpoint.cpp:154-188 これが adaptive watchpoint を成立させている低レベルの契約であり、コメントに詳しく説明されている。

2 段目の PropertyInlineCacheClearingWatchpoint は、stub に 1 つでも watchpoint が付いている場合にだけ作られ、InlineCacheHandler が所有する。bytecode/InlineCacheCompiler.cpp:7203-7215 CodeBlock が死ぬときには aboutToDie() でこれを先に破棄し、死んだ CodeBlock に向かって発火することが無いようにしている。bytecode/InlineCacheHandler.cpp:239-247

条件集合以外にも、stub には次の watchpoint set が追加で結び付けられることがある（collectAdditionalWatchpoints bytecode/InlineCacheCompiler.cpp:4625-4653）。impure property（DOM の名前付きプロパティのように C++ 側が黙って生やしうるもの）の出現を通知する VM 単位の set、PropertySlot が明示的に指定した set（WebCore の window オブジェクトが使う）、そして poly proto への転換を通知する共有 set である。

11.3置換 watchpoint：get IC と put IC の相互作用

Structure は、プロパティごとに「その値が置き換えられた」ことを通知する置換 watchpoint set を持てる（StructureRareData::m_replacementWatchpointSets）。runtime/Structure.cpp:1129-1163 IC の観点で重要なのは、get IC と put IC がこれを逆方向から扱っている点である。

  • get 側：Load ケースを生成するとき、startWatchingPropertyForReplacements() でその set を作成し監視状態にする。bytecode/InlineCacheCompiler.cpp:3232, 7276, bytecode/Repatch.cpp:591 IC 自身は値をキャッシュしていないのでこの通知を必要としないが、後で DFG が「このプロトタイプの x は常にこの関数である」と定数畳み込みしたくなったとき、監視が既に始まっていれば直ちに利用できる。
  • put 側：Replace ケースを生成するとき、didCachePropertyReplacement() でその set を発火させてしまう。bytecode/Repatch.cpp の tryCachePutBy, runtime/StructureInlines.h:203-207 以後この IC はスローパスを通らずに値を書き換えるので、「値は変わっていない」という仮定はもう守れない、と先に宣言しておくわけである。発火済みの set は Equivalence 条件が「監視不能」と判定する根拠になり（§11.1）、DFG はそのプロパティの畳み込みを諦める。

つまり、ある Structure のあるプロパティに対して書き込みサイトが 1 箇所でも IC 化された時点で、その Structure を持つオブジェクトのそのプロパティに関する定数畳み込みは、どこで行われようと自動的に無効になる（置換 set は Structure ごと・オフセットごとに 1 つである）。IC が単なるキャッシュにとどまらず、最適化コンパイラへの情報源としても振る舞っている例であり、§12 の主題につながる。

11.4GC との関係

IC は Structure・プロトタイプ・保持元・getter 関数など多数のセルを参照するが、これらを強参照にはしない。IC がオブジェクトを延命させると、既に不要になったクラスの Structure がコードの寿命の間ずっと残ってしまうからである。IC が強参照するのは CacheableIdentifier が保持するプロパティ名セル（by-val 用。§11.5）だけで、bytecode/PropertyInlineCache.cpp:400-430 それ以外はすべて弱参照である。GC は次の 3 段階で IC を扱う。

  1. マーク中：遷移の伝播（propagateTransitions）。Transition ケースは「旧 Structure が生きているなら新 Structure も生かす」という条件付きのマークを行う。bytecode/AccessCase.cpp:1418-1442, bytecode/CodeBlock.cpp:1335-1435 旧 Structure のオブジェクトがまだ存在するなら、その遷移先はまた使われる可能性が高いからである。逆に旧 Structure が死んでいれば、新 Structure を IC のために延命する理由は無い。この判定は他のセルのマーク状況に依存するので、マークが収束するまで繰り返し実行される（output constraint）。また、通常の Structure についても markIfCheap()——プロトタイプと realm が既にマークされている場合に限りマークする——が行われる。runtime/Structure.cpp:1461-1480
  2. GC 終了時：点検とリセット（reconcileWeakReferencesAtGCEnd）。各 IC について、inline access の Structure、各 handler の AccessCase が依存する全セル（isStillLive()）、個別生成 stub に焼き込まれた弱参照 Structure（m_weakStructures）を点検し、1 つでも死んでいれば IC 全体を reset() して resetByGC を立てる。bytecode/PropertyInlineCache.cpp:434-478, bytecode/InlineCacheHandler.cpp:249-262 ケース単位ではなく IC 単位でリセットするのは実装の単純さのためで、死んだ形はもう来ないのだから、生き残るべきケースは次のスローパスですぐに再生成される。
  3. stub の機械語の解放（GCAwareJITStubRoutine）。stub の機械語は、IC からの参照が消えた瞬間に解放してはならない。その stub が getter を呼び出している最中（＝スタック上に戻り番地がある）かもしれないからである。そこで GCAwareJITStubRoutine は参照カウントが 0 になっても m_isJettisoned を立てるだけにとどめ、jit/GCAwareJITStubRoutine.cpp:55-71 次の GC が保守的スタックスキャンで「どの stub のアドレスもスタック上に無い」ことを確認してから実際に解放する。heap/JITStubRoutineSet.cpp:133-171 逆に、実行中と判明した stub については、その stub が呼び出し後に使うセル（cellsToMark）をマークする。これが §8.6 で述べた「リセットが実行中に起きても安全」の根拠である。

11.5補足：CacheableIdentifier と by-val IC

o[k] のような by-val アクセスも、k が実行時に文字列や Symbol であれば by-id と同じ仕組みでキャッシュされる。このときガードには「structureID が一致」に加えて「キーが同じ名前である」という検査が要る。JSC ではプロパティ名として使われる文字列は atom 化（内容ごとに一意な UniquedStringImpl に正規化）されているので、この検査はimpl ポインタの比較 1 回で済む。bytecode/InlineCacheCompiler.cpp:1856-1866, 1413-1430 ただし、そのためには比較対象の impl が解放・再利用されないことを保証する必要があり、これが CacheableIdentifier の役目である。by-val の IC はキーのセルを CacheableIdentifier として保持し、GC 時に visitAggregate で強くマークする。runtime/CacheableIdentifier.h:93-99, runtime/CacheableIdentifierInlines.h:167-171 セルが生きていれば impl も生きているので、焼き込んだポインタは有効であり続ける。by-id の場合は名前が CodeBlock の識別子表に含まれているので、この保持は不要である。

12.4この設計が意味すること

以上を踏まえると、JSC の階層構造における IC の位置づけは次のように整理できる。

  • LLInt の ICは、インタプリタ自身の高速化と、Baseline の inline 検査の形を決めるヒント（§8.3）を提供する。
  • Baseline の ICは、Baseline コードの高速化であると同時に、DFG にとっての主要なプロファイルである。Handler IC が「安く育つ」ことを重視している（§3.1）のは、この段階の主目的が観測の収集だからでもある。
  • DFG の ICは、展開できなかったサイトの受け皿であり、かつ FTL への再コンパイルのためのプロファイルである。
  • FTL の ICは純粋に実行速度のための最終手段であり、だからこそ生成コストの高い Repatching 方式が許される。

「観測した事実を宣言的なデータ（AccessCase）として持ち、それを機械語にもプロファイルにも翻訳できるようにする」という一点が、この全体を成立させている。

13.2観察例

次のプログラムは、1 つのアクセスサイト p.x に対して形の数を変えながら実行する。jsc シェルの describe(o) は Structure のアドレスを表示するので、同じ形かどうかを確認できる。

// jsc --useICStats=true --exposeProfilersOnGlobalObject=true --useDFGJIT=false ic.js
const SHAPES = 4;                              // 1, 4, 12 に変えて比較する

function read(p) { return p.x; }             // ← 観察対象のサイト
noInline(read);

function make(n) {                             // p0 .. p(n-1) を持つ n 番目の形を作る
    const o = { x: n };
    for (let i = 0; i < n; ++i) o["p" + i] = i;    // 追加するたびに Structure が遷移する
    return o;
}
const shapes = [];
for (let n = 1; n <= SHAPES; ++n) shapes.push(make(n));

__signpostStart();
for (let i = 0; i < 1e5; ++i) read(shapes[i % SHAPES]);
__signpostStop();

SHAPES を 1 にすれば単相——OperationGetByIdOptimize がおおむね 2 回（§5.4 の countdown のぶん）、GetByAddAccessCase と GetByReplaceWithJump が 1 回ずつで、以後イベントが止まる（Baseline では生成された handler が inline 検査に昇格している。FTL まで動かせば代わりに GetBySelfPatch が現れる）。4 にすれば GetByAddAccessCase が 4 回、12 にすれば 8 回目のケース追加の後に megamorphic 化して Optimize 系イベントが止まる様子が、それぞれ統計に現れるはずである。--useDFGJIT=false を外すと、DFG が §12 の展開を行ってサイトから IC が消えるため、統計の伸びが途中で止まる様子も観察できる。

なお、読むプロパティを p.x から p.p0 に変えると、--dumpDisassembly=true の出力で butterfly をロードしてから値を読む形（図 2.1 の out-of-line 側）が現れる。オブジェクトリテラルの inline 容量はバイトコードコンパイラがリテラル中に静的に見えるプロパティ数（ここでは x の 1 個）から決めるため、bytecompiler/BytecodeGenerator.cpp:6020-6029 後からループで足した p0 以降はすべて out-of-line に置かれるからである。$vm.dumpCell(shapes[0])（--useDollarVM=true）で実際の配置を確認できる。

13.3演習

  1. §4 の GetByIdModeMetadata で、ProtoLoad の列挙値が 0 でなければならない理由を、図 4.1 のバイト配置を用いて説明せよ。また、Default モードのメタデータをリンク直後の状態（structureID = 0）にしておくと必ずミスする理由を述べよ。
  2. inline 容量 6 の JSFinalObject がプロパティ 3 個を持つ状態で 4 個目のプロパティを追加するとき、（a）LLInt、（b）Handler IC のいずれで遷移がキャッシュされるか。プロパティが 6 個ある状態で 7 個目を追加する場合はどうか。§2.3 と §7.3 の 4 形態を用いて答えよ。
  3. o.x が o の 2 段上のプロトタイプ Q で見つかるとする（o → P → Q）。tryCacheGetBy が生成する条件集合の中身を列挙し、それぞれが「監視」と「検査」のどちらになりうるかを、P と Q の Structure の状態ごとに述べよ（§6.4, §11.1）。
  4. Handler IC で、あるサイトに Structure S₁, S₂, S₃ の順で形が現れた後、S₁ が最も頻繁に来るようになったとする。ガードの実行順序はどうなるか。Repatching IC（binary switch）の場合と比較せよ（§8.2, §9.4）。
  5. countdown の初期値が 1 であることから、Baseline のあるサイトが最初に実行されてから IC が最初のケースを覚えるまでに、そのサイトは何回スローパスを通るか（§5.4）。この設計の利点を、1 回しか実行されないコード（初期化コード）の観点から説明せよ。
  6. Object.prototype に新しいメソッドを追加すると、その時点で存在する get IC のうち、どの種類のものが無効化され、どの種類のものが生き残るか。adaptive watchpoint（§4.4, §11.2）を踏まえて答えよ。
  7. MegamorphicCache が dictionary な base を扱えない理由と、サイト単位の IC が cacheable dictionary の自己アクセスなら扱える理由を対比して説明せよ（§2.4, §10.3）。
  8. put IC の Replace ケースを生成するときに置換 watchpoint set を発火させるのに対し、get IC の Load ケースは監視を開始するだけである。もし Replace ケース生成時に発火させなかった場合、DFG がどのような誤ったコードを生成しうるか、具体例を挙げよ（§11.3）。
  9. GC が Structure を弱参照としてしか扱わないにもかかわらず、Transition ケースの新 Structure については条件付きでマークする（§11.4）。この非対称の理由を述べ、条件付きマークを行わなかった場合に起きる性能上の問題を説明せよ。
  10. 設計問題：Handler IC を FTL にも適用する場合（useHandlerICInFTL）、現在の実装のどの前提が問題になるか。§5.1 のレジスタ規約と §9.1 の B3 によるレジスタ割当を手がかりに考察せよ。

§14まとめ・用語集・ソースマップ

14.1本章の要点

  1. IC は「ガード・ペイロード・スローパス・無効化」の 4 部品からなる。JSC ではガードが StructureID の 32bit 比較に、ペイロードが (Structure, PropertyOffset[, holder]) の組に還元される。これはオブジェクト表現（§2）がそう設計されているからである。
  2. 階層ごとに記憶域の形が違う。LLInt はメタデータ（§4）、Baseline／DFG は InlineCacheHandler の連結リスト（§8）、FTL は書き換え可能な機械語スラブ（§9）。しかし「何をキャッシュするか」の判断（§6）と「1 ケースの記述」（AccessCase、§7）は JIT 階層で共通である。
  3. Handler IC はケース追加を「データ構造へのノード追加」にし、機械語を VM 全体で共有することで生成コストを最小化した。Repatching IC は専用コードと binary switch で実行速度を最大化する。生成コストと実行速度のどちらを優先するかが、階層ごとの方式選択の基準である（§3.1）。
  4. 他オブジェクトに関する仮定は条件集合として宣言的に持ち、コード生成時に「監視」か「検査」かを決める。監視は adaptive watchpoint により、無関係な変更では壊れない（§11）。
  5. 形の数が 8 を超えると、サイト単位の IC から VM 全体の MegamorphicCache へ切り替わる。こちらは epoch による大雑把な一括無効化で運用される（§10）。
  6. IC は参照先を弱参照で持ち、GC 終了時に点検してリセットする。stub の機械語はスタック上に無いことを GC が確認してから解放する（§11.4）。
  7. 下位階層の IC は上位階層のプロファイルである。AccessCase は GetByStatus を経て DFG／FTL の構造検査とロード（あるいは getter のインライン展開）に変換され、最終的に IC 自体が消える（§12）。
