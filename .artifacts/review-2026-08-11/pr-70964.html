概要

Worker が Atomics.wait()（または Wasm の memory.atomic.wait32/64）で無限にブロックしている最中に worker.terminate() を呼ぶと、bug 305440 の変更以降、Worker スレッドが終了しなくなっていた回帰を修正します。

根本原因: notifyNeedTermination() は現在 VMTraps::NeedTermination のトラップビットを立てるだけで、VM::hasTerminationRequest() を即座には true にしなくなりました。WaiterListManager::waitSyncImpl は stop-request の condition notify で起床はするものの、起床後のチェックが hasTerminationRequest() しか見ていなかったため Terminated を返さず、そのままループし続けていました。

背景 — なぜハングするか

終了通知の 2 段階化（bug 305440 の変更）

以前は VM::notifyNeedTermination() が即座に m_hasTerminationRequest = true を立てていました。bug 305440 で「まず VMTraps::NeedTermination ビットを立てる → mutator 側が次のトラップチェックポイントで handleTraps() を呼ぶ → その中で setHasTerminationRequest() + throwTerminationException()」という 2 段階に変更されました（DeferTermination スコープとの整合のため）。

waitSyncImpl の起床パス

waitSyncImpl は condition().waitUntil() でブロックし、以下 3 つのいずれかで起きます。

  • Atomics.notify() による dequeue → OK
  • timeout → TimedOut
  • VM stop 要求 — VMBlockingScope が登録した stop-request 用 condition が notify される（VMManager が全 blocked VM を起こす仕組み）

3 番目で起きた場合、旧コードは:

while (syncWaiter->isOnList() && time.now() < time && !vm.hasTerminationRequest())
    syncWaiter->condition().waitUntil(...);
// ↑ hasTerminationRequest() はまだ false（NeedTermination ビットのみ）
// → 条件が全て true → waitUntil() へ再突入 → ハング

変更内容の詳細

1. WaiterListManager.cpp — waitSyncImpl

終了判定を「hasTerminationRequest() または traps().needHandling(NeedTermination)」に拡張。起床後は notify/timeout との競合よりも Terminated を優先し、まだリストに残っていれば自分でリストから除去します。

auto isTerminating = [&] {
    return vm.hasTerminationRequest() || vm.traps().needHandling(VMTraps::NeedTermination);
};
...
while (syncWaiter->isOnList() && time.now() < time && !isTerminating())
    syncWaiter->condition().waitUntil(list->lock, ...);

if (isTerminating()) {
    if (syncWaiter->isOnList())
        list->findAndRemove(listLocker, syncWaiter);
    return WaitSyncResult::Terminated;    // notify/timeout と競合しても Terminated を優先
}
// 以降は既存の OK / TimedOut パス

2. VM.cpp — 新関数 throwTerminationExceptionIfNeeded()

Terminated を返された呼び出し元が使うヘルパー。

void VM::throwTerminationExceptionIfNeeded() {
    if (hasPendingTerminationException()) return;       // 既に投げ済み
    if (traps().needHandling(VMTraps::NeedTermination))
        traps().handleTraps(VMTraps::NeedTermination);  // トラップを処理 → 例外を投げる
    if (hasPendingTerminationException()) return;
    if (hasTerminationRequest() && !traps().isDeferringTermination())
        throwTerminationException();                    // フォールバック
}

3. AtomicsObject.cpp / WasmOperationsInlines.h — 呼び出し側

Terminated ケースで throwTerminationException() の直呼びを throwTerminationExceptionIfNeeded() に置換。Wasm 版は -1 を返します（既存と同じ）。

4. WasmOperationsInlines.h — throwWasmToJSException

Wasm の各 tier（BBQ/OMG/IPInt）は wait の返り値が負なら ExceptionType::OutOfBoundsMemoryAccess でこの関数に飛びます。Terminated パスでは既に TerminationException が投げられているので、それを上書きせず単に unwind します。

if (vm.hasPendingTerminationException())
    break;                                  // 既存の TerminationException を保持
if (type == ExceptionType::Termination) {
    RELEASE_ASSERT_NOT_REACHED();           // このパスに来ることはもう無い
    break;
}

5. LayoutTests

Worker が postMessage("ready") → 無限 wait に入る → 親が terminate() → internals.workerThreadCount が 0 になるまで GC + poll。JS 版と Wasm 版の 2 本。

コードレビュー結果

総評: 修正の方向性は正しく、全 tier（LLInt/Baseline JS、IPInt/BBQ/OMG Wasm）で終了パスが一貫して TerminationException に収束することをコード追跡で確認しました。ただしいくつかコメントに値する点があります。

敵対的レビューで検証した項目

  • ✅ traps().needHandling(NeedTermination) は list->lock 保持中に呼ばれるが、これは atomic bit の read のみでロック取得しない → デッドロックなし
  • ✅ throwWasmToJSException の RELEASE_ASSERT_NOT_REACHED() — type == Termination で到達するのは WasmIPIntSlowPaths.cpp の IPINT_THROW(Termination) のみで、そこは hasPendingTerminationException() が真の場合しか通らないため、直前の early-break で回避される。到達不能で正しい。
  • ✅ BBQ (WasmBBQJIT.cpp:1346)・OMG (WasmOMGIRGenerator.cpp:3230)・IPInt (InPlaceInterpreter64.asm:10126) いずれも wait 返り値 < 0 で OutOfBoundsMemoryAccess をスローし、新コードで hasPendingTerminationException() により正しく TerminationException が保持される
  • ✅ Terminated 優先により「notify と terminate の競合」で "ok" が返らなくなるが、これは仕様上問題なし（terminate 後の Worker 実行結果は observable でない）

指摘事項

LOW PLAUSIBLE Source/JavaScriptCore/runtime/VM.cpp — throwTerminationExceptionIfNeeded()
DeferTermination スコープ内で Atomics.wait がブロックしていた場合、Terminated は返るが例外が投げられず、Wasm 側では偽の OutOfBoundsMemoryAccess エラーが投げられる可能性があります。
シナリオ
isDeferringTermination() が真のとき: handleTraps(NeedTermination) は mask &= ~NeedTermination で何もせず戻り、フォールバックの throwTerminationException() も !isDeferringTermination() ガードで実行されません。すると waitImpl は -1 を返しますが hasPendingTerminationException() は false のまま → Wasm JIT が throwWasmToJSException(OutOfBoundsMemoryAccess) を呼び、TerminationException ではなく通常の WebAssembly.RuntimeError が投げられます。
検証結果
実際には DeferTermination は FTLOperations::materialize・Interpreter::unwind・ExceptionHelpers マクロなど、VM 内部の限定的なスコープでのみ使われており、そのスコープ内から Wasm の atomic.wait や JS の Atomics.wait に到達するパスは通常存在しません。よって実運用で発火する可能性は極めて低いです。
推奨対応
念のため throwTerminationExceptionIfNeeded() の末尾に ASSERT(hasPendingTerminationException() || traps().isDeferringTermination()) を追加し、想定外のパスがあれば Debug ビルドで検出できるようにすると安全です。ブロッキングではありません。
LOW PLAUSIBLE Source/JavaScriptCore/runtime/VM.cpp — throwTerminationExceptionIfNeeded()
handleTraps(NeedTermination) は codeBlockSet ロック取得 + 全 CodeBlock 走査（VMTraps breakpoint jettison）を無条件に行うため、Atomics.wait の Terminated パスで想定外のオーバーヘッドとロック取得が発生します。
シナリオ
VMTraps::handleTraps() の冒頭は vm.heap.codeBlockSet().getLock() を取得して全 CodeBlock を走査します（VMTraps.cpp:454-460）。これは通常のトラップチェックポイント（バイトコード境界）で呼ばれる想定のコードで、waitSyncImpl の直後という新しい呼び出し文脈でも安全か（他のロックとの順序）は自明ではありません。
検証結果
waitSyncImpl から戻った時点で list->lock と VMBlockingScope は既に解放済み（RAII スコープを抜けている）で、mutator スレッドは通常の実行状態にあるため、デッドロックは発生しません。オーバーヘッドは terminate パスでのみ発生し、terminate 自体が稀なので許容範囲です。
推奨対応
コメント程度。handleTraps を呼ぶのが最も正しい動作（setHasTerminationRequest() と throwTerminationException() を正規の順序で行う）なので、このままで問題ありません。
NIT LayoutTests/fast/workers/resources/worker-atomics-wait-forever.js
JS 版テストで Worker 側の SAB は Worker ローカルに作られており、親と共有されていません。
シナリオ
Wasm 版は shared: true の Memory を使いますが Worker ローカルです。JS 版も new SharedArrayBuffer(4) を Worker 内で作り、Atomics.wait でブロックします。誰も notify しないので無限 wait になり、テストの目的（terminate で起こす）は達成されます。
検証結果
テストの目的（wait 中の terminate）には十分です。ただし postMessage("ready") と Atomics.wait() の間に極小の race window があり、非常に遅い環境で terminate() が wait 突入前に届く可能性があります。Wasm 版は 50ms 待ってから terminate しており、JS 版も同様の delay を入れると堅牢性が上がります。
推奨対応
任意。既存の類似テスト（worker-terminate-forever.html 等）と同水準なのでそのままでも可。

敵対的レビュー結果: 2 名の独立レビュアーが上記 1 番目（DeferTermination edge case）と同一の指摘を報告。反証エージェントが全 DeferTraps/DeferTermination 使用箇所（RepatchInlines.h・Interpreter.cpp・LLIntSlowPaths.cpp・JITOperations.cpp・DFGOperations.cpp・BytecodeGenerator・LazyProperty 他）を監査した結果、いずれも prepareForExecution/linking/初期化のみを囲み、ユーザー JS/Wasm 実行前にスコープが終了することを確認。現行コードで到達可能なパスは存在しない（PLAUSIBLE / defense-in-depth のみ）。
