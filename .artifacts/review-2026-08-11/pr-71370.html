概要

この PR は 2 つの独立した小変更をまとめたものです。

  1. デッドコード削除 — CalendarICUBridge.cpp の lunarCalendarExtendedYearFor1972() 関数（32 行、+ ヘッダ宣言）を削除します。この関数は中国暦・檀紀暦の ICU バージョン差異（ISO-proleptic 年 vs epoch 起点年）を判定するプローブでしたが、constrainMonthCodeInternal が positionCalendarToYearStart の書き戻す年フィールドを直接読むようになった結果、呼び出し元がゼロになっていました。
  2. 回帰テスト 3 本の追加 — Temporal 実装の監査で洗い出された仕様準拠エッジケース（monthCode の型強制、relativeTo のフィールド読み取り順序、PlainDate.prototype.with のオプション読み取りタイミング）を JSTests/stress/ に固定します。

実装コードの動作変更は一切なく、テスト追加とクリーンアップのみです。

背景 — なぜこの変更が必要か

デッドコード lunarCalendarExtendedYearFor1972

ICU は歴史的に中国暦（chinese）と檀紀暦（dangi）の UCAL_EXTENDED_YEAR を「epoch 起点年」（例: ISO 1972 → 中国暦 4609 年）で返してきましたが、ICU 76 以降は「ISO-proleptic 年」（そのまま 1972）を返す挙動に切り替わりました。JSC の Temporal 実装は当初この差を吸収するために、既知の日付（ISO 1972-02-15）で ICU に問い合わせて実際の返値を観測し、その結果をプロセス寿命にわたってキャッシュするプローブ関数を持っていました。

しかし後続の実装リファクタで、月コード制約ロジック（constrainMonthCodeInternal）が「まず positionCalendarToYearStart で ICU カレンダーを年頭に位置付け → その位置で ICU が書き戻した実際の EXTENDED_YEAR をそのまま読む」方式に変更されました。これにより ICU バージョンごとの返値差はその場で自然に吸収されるため、事前プローブは不要になりました。

コードベース全体を git grep で検索した結果、削除後のブランチに lunarCalendarExtendedYearFor1972 の参照は 0 件です（TestAPI・jsc.cpp・LayoutTests 含む）。JS_EXPORT_PRIVATE 付きでしたが、WebCore/WebKit 側にも呼び出し元はありません。安全に削除できます。

追加される 3 つのテスト

Temporal 仕様はプロパティバッグからのフィールド読み取り順序と型検証タイミングを厳密に規定しており、observable な副作用（getter 呼び出し順・例外の種類）が仕様と一致しなければなりません。今回追加されるテストは、いずれも「JSC は現状正しく動くが、リファクタで壊れやすい」観測可能な挙動を固定するものです。

変更内容の詳細

1. temporal-monthcode-wrong-type.js

monthCode フィールドは仕様上「? ToPrimitive(value, string) → 文字列でなければ TypeError → monthCode 文法検証 → RangeError」の順で処理されます（PrepareCalendarFields）。テストは以下を確認します。

  • 数値・真偽値・BigInt・Symbol・null を monthCode に渡すと TypeError（from() と with() の両方、PlainDate/PlainDateTime/PlainYearMonth/PlainMonthDay の全型）
  • 不正な文字列（例: "bogus"）は RangeError
  • オブジェクトは ToPrimitive で文字列化 — toString() が正しい monthCode を返せば受理、不正なら RangeError（TypeError ではない）
  • toString() は正確に 1 回だけ呼ばれる
  • 文法検証（"L99M" は文法不正 → RangeError）とカレンダー適合検証（"M99L" は文法上有効だが ISO カレンダーに存在しない → 後続の year 検証で TypeError）の順序

2. temporal-plaindate-with-option-order.js

PlainDate.prototype.with(fields, options) は仕様上「フィールド読み取り → 空バッグなら TypeError → その後 options.overflow 読み取り → month/monthCode 矛盾チェック」の順序です。テストは overflow getter に副作用を持たせて、以下を確認します。

  • {month: 3, monthCode: 'M04'}（矛盾） → overflow は先に読まれる（RangeError の前にログに残る）
  • 空バッグ {} → overflow は読まれないまま TypeError
  • 正常系で overflow は正確に 1 回読まれる
  • 非 ISO カレンダー（gregory）でも同じ順序

3. temporal-relativeto-field-order.js

Duration.prototype.total/round の relativeTo オプションは、プロパティバッグから calendar → day → hour → … → timeZone → year をアルファベット順に読み取り、各フィールドをその読み取り位置で型変換します。テストは以下を確認します。

  • timeZone に数値 5 を渡す → year を読む前に TypeError（getter ログ: day,month,timeZone のみ）
  • 全 13 フィールドが未定義 → 全て読まれてから missing-field TypeError
  • 不正な timeZone 文字列は RangeError（TypeError ではない）
  • 正常系で timeZone getter は正確に 1 回

4. CalendarICUBridge.{cpp,h}

関数本体（32 行）とヘッダ宣言（JS_EXPORT_PRIVATE 付き）を削除。static std::atomic<int32_t> 2 個も削除されます。
