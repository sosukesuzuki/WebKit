概要

WebAssembly の検証（validation）において、到達不能コード内でも型スタックを追跡し、仕様が要求する型不一致を検出するようにします。これにより WPT の unreached-invalid.wast・call_ref.wast・return_call_ref.wast で計 42 個 の FAIL → PASS が達成されます。

変更は WasmFunctionParser.h の parseUnreachableExpression() のみに集中しています（+530 行程度）。実装コード生成には影響せず、検証ロジックのみの変更です。

背景 — Wasm 仕様の polymorphic stack

仕様が要求すること

Wasm の型検証は「フレームごとに型スタックを保持し、各命令が pop/push する型が合うか」を確認します。unreachable・br・return・throw 等の制御が戻らない命令の直後は、仕様上スタックが「polymorphic（多相）」状態になります（Validation Algorithm §Appendix）。

  • polymorphic 状態では任意個の ⊥（bottom 型）を pop できる
  • ただし、unreachable の後に push された具体値は追跡され、後続命令が pop する期待型と一致しなければ検証エラー

つまり以下は不正なモジュールです（仕様上コンパイル失敗しなければならない）:

(func (result i32)
  unreachable
  i64.const 0     ;; スタック: [i64]
  i32.eqz)        ;; i32 を pop したいが i64 → 型エラー！

JSC の現状（この PR 以前）

JSC の parseUnreachableExpression() は immediates のパースと基本的な index 検証のみを行い、型スタックの追跡をしていません。そのため上記のような「到達不能コード内の型不一致」を検出できず、unreached-invalid.wast の多くの assert_invalid テストで「不正なモジュールを受理してしまう（false accept）」失敗になっていました。

実行時の危険性はありません（到達不能なので実行されない）が、仕様準拠度と web-platform-tests のスコアに影響します。

変更内容の詳細

1. 新しいパーサー状態

bool m_unreachablePolymorphic { false };       // 現フレームが polymorphic 状態か
Vector<Type, 16> m_unreachableTypeStack;       // polymorphic 突入後に push された具体型

m_unreachableTypeStack は型のみを保持し、生成器（BBQ/IPInt）の m_expressionStack とは別に管理されます（生成器側は到達不能コード内の値を必要としないため）。

2. ヘルパー関数群

関数役割
markUnreachableAndClearStack()到達可能 → 到達不能への遷移。type stack をクリアし polymorphic に。
truncateUnreachableStack()到達不能内で再び polymorphic になる（br・return・throw 等）。
pushUnreachableOperand(Type)型を type stack に push。
popUnreachableOperand(expected, &actual)type stack が空でなければ pop して isSubtype(actual, expected) を検証。空かつ polymorphic なら ⊥ を pop（= expected を返す）。空かつ非 polymorphic ならエラー。
popUnreachableBranchArgs(target)ブランチターゲットの label 型列を（末尾から）pop して検証。
checkUnreachableBranchTarget(target)消費せずに label 型列を検証（br_table の複数ターゲット用）。

3. reachable → unreachable 遷移点の統一

Br・BrTable・Return・Unreachable・Throw・ThrowRef・Rethrow・TailCall* の 10 か所で m_unreachableBlocks = 1 を markUnreachableAndClearStack() に置換。

4. parseUnreachableExpression() の各 opcode 対応

m_unreachableBlocks == 1（= 最外の到達不能フレーム）のときのみ型追跡を行います。ネストした到達不能ブロック内（m_unreachableBlocks > 1）は従来どおり immediates のパースのみです。

主な追加内容:

  • 数値定数（I32Const 等）→ 対応型を push
  • 単項/二項演算 → FOR_EACH_WASM_{UNARY,BINARY}_OP マクロで operand/result 型を pop/push
  • load/store → address 型と value 型を pop/push
  • local/global get/set → index の型で pop/push
  • call/call_indirect/call_ref → シグネチャの引数を pop、返り値を push（tail call は truncate）
  • br/br_if/br_table/return → target の label 型を検証してから truncate
  • select → 3 つ pop、両オペランドが具体値なら型一致検証、ref 型なら reject
  • ref.null/ref.func/ref.is_null/ref.as_non_null/ref.eq → ref 型を push/pop
  • table.*・memory.*（ext1 系）→ 各命令のシグネチャ通り
  • wide-arithmetic（i64.add128 等）→ 4 pop / 2 push
  • 未対応の複雑な opcode（GC 系 ExtGC・SIMD ExtSIMD・atomics ExtAtomic・BrOnNull/BrOnNonNull）→ truncateUnreachableStack() で polymorphic empty にリセット（= 型追跡を諦める。false accept は残るが false reject はしない）。

5. WPT expectation 更新

unreached-invalid.wast.js-expected.txt で 38 個、call_ref・return_call_ref で各 2 個の FAIL → PASS。

コードレビュー結果

総評: 大きな一歩前進で、多くの WPT が新たに PASS します。設計の方針（type-only stack + polymorphic フラグ、未対応 opcode は保守的に truncate）は健全です。ただし br_table の部分スタック検証と、いくつかのエッジケースについてコメントに値する点があります。

敵対的レビューで検証した項目

  • ✅ parseBranchTarget(target, m_unreachableBlocks) で m_unreachableBlocks == 1 のとき controlStackSize += 0 なので target < m_controlStack.size() が保証され、m_controlStack[size - 1 - target] は範囲内
  • ✅ Void 型を「polymorphic からの発明値」の sentinel として使用 — Wasm 型システムに Void は現れないので衝突しない
  • ✅ Else/Catch/CatchAll/End で m_unreachableBlocks == 1 のとき type stack と polymorphic フラグを正しくリセット
  • ✅ 未対応 opcode（GC/SIMD/atomics/BrOn*）は truncateUnreachableStack() で safe な over-approximation — false reject しない
  • ✅ Try（legacy 例外）で m_usesLegacyExceptions.storeRelaxed(true) を到達不能パスでも設定するように追加（副次的な修正）
  • ✅ 到達可能パスの Br で markUnreachableAndClearStack() の呼び出し位置を addBranch() の後に移動 — addBranch は expressionStack() を参照するので先にクリアしてはいけない。移動は正しい。

指摘事項

MEDIUM CONFIRMED WasmFunctionParser.h — checkUnreachableBranchTarget()
br_table で type stack に arity 未満の具体値しかない場合、非 default ターゲットに対する具体値の型検証がスキップされます（false accept）。
シナリオ
(block $A (result i32 i32) ...)   ;; label 型 [i32, i32]
(block $B (result i32 f32) ...)   ;; label 型 [i32, f32]
unreachable
f32.const 0      ;; type stack = [f32], polymorphic
i32.const 0      ;; index
br_table $A $B
checkUnreachableBranchTarget($A): sliceSize=1 < arity=2 かつ polymorphic=true → 早期 return（f32 vs i32 の検証を飛ばす）。popUnreachableBranchArgs($B): f32 vs f32 ✓、⊥ vs i32 ✓ → 受理。しかし仕様上 $A に対して [⊥, f32] を [i32, i32] として pop できないので reject すべき。
検証結果
checkUnreachableBranchTarget() の if (sliceSize < arity) { ... return { }; } パスでは m_unreachableTypeStack の中身を一切見ていません。仕様アルゴリズムは「polymorphic pop は具体値を先に消費し、足りない分だけ ⊥ を発明する」なので、具体値部分の型不一致は検出しなければなりません。
影響度
これは regression ではありません（この PR 以前は到達不能コードで一切型検証していなかったので、同じモジュールは以前も受理されていた）。false accept のみで false reject はなく、実行時の危険もありません。ただし WPT に該当ケースが今後追加される可能性があります。
推奨対応
sliceSize < arity の early-return 前に、m_unreachableTypeStack の具体値を target.branchTargetType(arity - sliceSize + i) と照合するループを追加。
LOW CONFIRMED WasmFunctionParser.h — parseUnreachableExpression() BrTable
到達不能 br_table で targetIndices.reserveInitialCapacity(numberOfTargets) は OOM 時にクラッシュします。到達可能パスは tryReserveCapacity + WASM_ALLOCATOR_FAIL_IF を使っています。
シナリオ
numberOfTargets は UINT32_MAX - 1 まで許容され、Vector<uint32_t>::reserveInitialCapacity(0xFFFFFFFE) は ~16 GB を要求します。実際には各ターゲットが最低 1 バイトの varint なので function body サイズに制約されますが、到達可能パスと同じ失敗モード（parser エラー）にすべきです。
推奨対応
WASM_ALLOCATOR_FAIL_IF(!targetIndices.tryReserveCapacity(numberOfTargets), ...) に変更（到達可能パスの :3873 と同じパターン）。
LOW PLAUSIBLE WasmFunctionParser.h — parseUnreachableExpression() BrOnNull/BrOnNonNull
br_on_null / br_on_non_null は単に truncateUnreachableStack() しており、ref オペランドの型検証も target 型検証も行いません。
シナリオ
unreachable; i32.const 0; br_on_null $L — 仕様上 br_on_null は ref 型を pop するので i32 は型エラーですが、この実装では検出されません。
影響度
commit message に「Untracked unreachable ops (GC, SIMD, atomics, br_on_*) reset the type stack to polymorphic empty」とあり、意図的な段階的実装です。false accept のみ。
推奨対応
本 PR の scope 内であれば ref 型検証だけでも追加すると WPT カバレッジが上がりますが、follow-up でも可。
NIT WasmFunctionParser.h — parseUnreachableExpression() BrTable
m_unreachableBlocks > 1 のときも targetIndices Vector に append しますが、使われません。
推奨対応
if (m_unreachableBlocks == 1) targetIndices.append(target); にすれば無駄な allocation を避けられます（あるいは Vector 自体を if ブロック内に移動）。
