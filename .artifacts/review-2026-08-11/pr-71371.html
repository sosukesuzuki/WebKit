概要

WasmGC の struct.new / array.new が生成する JIT コードを 2 点で最適化します。

  1. 定数セルサイズによるバンプアロケーション — 従来は「アロケータがレジスタに載っている（=変数）」場合はセルサイズもアロケータからロードしていましたが、WasmGC struct のセルサイズはコンパイル時に確定しているため、それを即値として埋め込めるようにします（メモリロード 1 つ削減）。
  2. B3 エフェクトモデルの緩和 — WasmStructNew / WasmArrayNew は従来 writes = HeapRange::top() と宣言していたため、割り当てを跨いだフィールドロードの CSE が無効化されていました。DFG の NewObject 系と同様に「新規オブジェクト以外には書き込まない」モデルに変更し、CSE を有効化します。

背景 — 現状の問題点

JIT アロケーションの高速パス

JSC のヒープは LocalAllocator ごとに free-list を持ち、高速パスは「free-list の intervalStart をロード → intervalStart + cellSize を書き戻し → 元の intervalStart を返す」バンプアロケーションです。ここで cellSize は通常アロケータの LocalAllocator::m_cellSize フィールドから load32 で取得します。

WasmGC struct の場合、struct 型ごとにレイアウトが固定なので cellSize = MarkedSpace::optimalSizeFor(JSWebAssemblyStruct::allocationSize(payloadSize)) はコンパイル時定数です。しかしアロケータ自体は JSWebAssemblyInstance の allocator 配列から動的にロードするため、JITAllocator は VariableNonNull モード（=「アロケータもセルサイズも変数」）で扱われ、cellSize のロードが省けませんでした。

B3 のエフェクトモデル

B3EliminateCommonSubexpressions は各命令の effects().writes を見て、キャッシュ中のロード（WasmStructGet 等）を無効化（clobber）します。WasmStructNew が writes = top だと、以下のパターンで 2 回目の struct.get が 1 回目と CSE できません。

local.set $sum (struct.get $s $f (local.get $a))   ;; 1回目のロード
drop (struct.new $t ...)                            ;; ← writes=top なので $a のロードキャッシュが飛ぶ
struct.set $s $f (local.get $a) ...
local.set $sum (struct.get $s $f (local.get $a))   ;; 2回目 — 直前の store から forwarding したい

実際には struct.new は「新規に確保したセルの中身」と「アロケータの free-list 状態」しか書き換えず、既存オブジェクトのフィールドは触らないため、この保守的なモデルは過剰でした。

変更 1: VariableNonNullWithConstantCellSize モードの追加

JITAllocator.h

4 番目の Kind として VariableNonNullWithConstantCellSize を追加。「アロケータはレジスタ渡し・null チェック不要・セルサイズは即値」を表現します。

static JITAllocator variableNonNullWithConstantCellSize(unsigned cellSize) {
    JITAllocator result(VariableNonNullWithConstantCellSize);
    result.m_cellSize = cellSize;
    return result;
}
bool hasConstantCellSize() const {
    return m_kind == Constant || m_kind == VariableNonNullWithConstantCellSize;
}
unsigned constantCellSize() const {
    if (m_kind == Constant) return m_allocator.cellSize();
    return m_cellSize;
}

AssemblyHelpers.cpp

emitAllocateWithNonNullAllocator の 3 か所（ARM64・x86-64・その他）で、allocator.isConstant() → allocator.hasConstantCellSize()、allocator.allocator().cellSize() → allocator.constantCellSize() に置換。emitAllocate() の switch にも新 Kind を追加（VariableNonNull と同じく null チェックを省く）。

B3LowerMacros.cpp / WasmBBQJIT64.cpp

セルサイズを MarkedSpace::s_sizeClassForSizeStep[sizeClassToIndex(sizeInBytes)] で取得し、variableNonNullWithConstantCellSize() で patchpoint に渡します。

正当性の鍵: JIT が計算する constantCellSize と、実行時にロードされる LocalAllocator::cellSize() は必ず一致することが不変条件です。

JSWebAssemblyInstance の allocator 配列は CompleteSubspace::allocatorsForSizeSteps() のコピーで、各エントリ [i] は allocatorForSlow(s_sizeClassForSizeStep[i]) で作られた LocalAllocator（cellSize = s_sizeClassForSizeStep[i]）です。JIT 側も同じ i = sizeClassToIndex(bytes) と s_sizeClassForSizeStep[i] を使うので、両者は表引きで一致します。

変更 2: B3 エフェクトモデルの緩和

B3Value.cpp

constantEffectsForOpcode で WasmStructNew / WasmArrayNew のエフェクトから result.writes = HeapRange::top() を削除。reads = top（GC が全ヒープを走査するため）と exitsSideways = true（OOM でトラップ・OSR exit 可能）は維持します。

case WasmStructNew:
case WasmArrayNew:
    // Allocation can trap and can trigger GC, so it reads everything and exits sideways.
    // It only stores into the object it just produced, though, which nothing loaded earlier
    // can alias, so it does not need to clobber previously cached field loads.
    result.reads = HeapRange::top();
    result.exitsSideways = true;
    break;

健全性の議論

この緩和で新たに可能になる最適化は「WasmStructNew / WasmArrayNew を跨いだ WasmStructGet/WasmArrayGet/MemoryValue Load の CSE」です。これが安全である理由:

  • 割り当てが書き込むのは (a) 新規セルの内容 (b) LocalAllocator の free-list 状態、のみ。既存オブジェクトのペイロードには一切書き込まない。
  • slow-path で GC が走っても JSC の MarkedSpace は non-moving なのでポインタは不変。GC はオブジェクトのペイロードを書き換えない（mark bit はヘッダ外）。
  • weak reference の clear は WasmGC struct フィールドには存在しない。
  • reads = top は維持されるので、割り当て前の store が割り当て後に沈むこと（reordering）は起きない。exitsSideways = true は維持されるので、割り当て後の副作用が割り当て前に浮くこともない。

これは DFG の NewObject/NewArray 等がずっと採用しているモデルと同じ（DFGClobberize.h）です。

追加テスト

  • struct-new-does-not-clobber-loads.js — 「read → alloc → store → read」のパターンで、2 回目の read が store の値（1 回目の値ではない）を見ることを 200,000 回ループで確認。CSE が誤って alloc 前の値を再利用すると失敗します。
  • struct-new-nested-alloc-gc.js — 入れ子の struct.new で大量にアロケートし、途中で GC が走っても外側 struct から内側 struct への参照が壊れないことを確認。

敵対的レビューで検証した項目

  • ✅ s_sizeClassForSizeStep[sizeClassToIndex(bytes)] = 実行時 LocalAllocator::cellSize() — CompleteSubspace::prepareAllAllocators() と buildSizeClassTable() を追跡して一致を確認
  • ✅ sizeClassIndex の範囲 — sizeInBytes ≤ largeCutoff のときのみ高速パスを取るので sizeClassIndex < numSizeClasses が保証される（B3LowerMacros.cpp:91 の条件変更後も同値）
  • ✅ 旧 (allocationSize + sizeStep - 1) >> stepShift と新 sizeClassToIndex(sizeInBytes) は同じ式（(size + sizeStep - 1) / sizeStep）
  • ✅ emitAllocate() の switch に VariableNonNullWithConstantCellSize ケース追加漏れなし
  • ✅ operator==(const JITAllocator&, const JITAllocator&) = default — m_cellSize フィールド追加後も defaulted 比較で全フィールド比較されるので問題なし
  • ✅ B3 CSE の clobber は effects.writes のみを見る（B3EliminateCommonSubexpressions.cpp:540）— exitsSideways だけではキャッシュを無効化しないので、緩和の効果は意図通り
  • ✅ WasmGC の slow-path C++ 呼び出し（operationWasmStructNew 等）は既存オブジェクトのペイロードに書き込まない
  • ✅ テスト struct-new-does-not-clobber-loads.js は「alloc 後の store → read」で store forwarding が正しく効くことを検証しており、緩和が過剰だった場合（alloc 前の read 値が再利用される場合）に検出できる設計
