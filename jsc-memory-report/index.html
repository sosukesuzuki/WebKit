This report is a source-level deep dive into JavaScriptCore's JIT tiers (LLInt → Baseline → DFG → FTL), inline caches, garbage collector and object model, focused on one question: where does memory attributable to JIT compilation — machine code and its metadata — go, and how could it be reduced? The tree is WebKit 7375405d8e (2026-08-16), built as JSCOnly Release on x86_64 Linux (clang 18, libpas JIT heap). Every number below was either measured on that build (a sizeof/record-layout harness compiled against the real headers, jsc shell runs of JetStream2 sub-tests with $vm.linkBufferStats(), JIT-pool RSS from /proc/pid/smaps, --dumpBaselineJITSizeStatistics/--dumpDFGJITSizeStatistics, an ENABLE(METADATA_STATISTICS) build, and a small temporary finalizer probe for retained DFG/FTL data) or is a static estimate derived from those measurements, and it is labelled as such.

The headline findings: (1) retained OSR-exit metadata dwarfs optimized machine code — for JetStream2 typescript the FTL keeps 9.75 MB of exit-value payload for 1.19 MB of FTL code and the DFG keeps a 3.94 MB event stream for 2.20 MB of DFG code; (2) Baseline code volume is dominated by generic inline IC sequences (get_by_id ≈ 93 B/site, 39% of the tier) and by giant straight-line functions that the size-blind LLInt threshold compiles anyway (Air: 5.7 MB of 6.5 MB), and it is pinned by the unlinked-baseline cache after CodeBlocks die; (3) bytecode metadata is dominated by the 80-byte DataOnlyCallLinkInfo embedded in every call site (30-40% of metadata bytes) and by IC objects that carry derivable or padding bytes (HandlerPropertyInlineCache 112 B, InlineCacheHandler 128 B with 32 B padding, a 96 B stub routine + 24 B watchpoint set per handler).

The 20 opportunities are ranked by (estimated saving ÷ risk); items 1-7 target executable memory, 8-13 and 18-19 metadata, 14-17 retained DFG/FTL data, 20 GC-side watchpoints. Existing savings mechanisms (unlinked Baseline sharing, handler ICs with ~99 shared thunks, 16-bit metadata offset tables, lazy OSR-exit compilation, shrinkToFit passes, old-age jettison, thin InlineWatchpointSets, 32-bit StructureIDs…) are catalogued in the deep-dive so that none of the proposals duplicates them.

Method & measurement setup方法と計測環境

Build

cmake -DPORT=JSCOnly -DCMAKE_BUILD_TYPE=Release -DDEVELOPER_MODE=ON -DENABLE_STATIC_JSC=ON with clang 18 on a 4-vCPU Linux VM (16 min). A second build added -DENABLE_METADATA_STATISTICS=1 (the counters in bytecode/UnlinkedMetadataTable.cpp exist upstream but are not wired to any option; they self-report at atexit) plus a 40-line, env-gated dataLog in DFG::Plan::finalizeInThread that counts retained per-compilation structures (patch in the appendix; reverted from the tree).

Static sizes

A translation unit including the real headers prints sizeof for ~115 types and -Xclang -fdump-record-layouts gives field offsets and padding (all sizes in this report are x86_64; Apple arm64 with 36-bit addresses shrinks a few CompactPtr fields).

Workloads

JetStream2 sub-tests run one at a time in the jsc shell through the JetStream driver in RAMification mode (typescript, acorn-wtb, Babylon, pdfjs, gbemu, Air, octane-zlib, ML, raytrace, splay) plus a synthetic 1-4K-function workload. After each run: two $vm.gc(), $vm.linkBufferStats() (cumulative linked bytes per LinkBuffer profile: Baseline/DFG/FTL/OSR exits/IC stubs/thunks), memoryUsageStatistics() (heap size, per-class cell counts), MemoryFootprint(), and — from a Python driver reading /proc/&lt;pid&gt;/smaps while the shell blocks on readline() — the RSS of the fixed 1 GB executable pool (sum of its contiguous anonymous rwxp VMAs). Configurations: default, --thresholdForJITAfterWarmUp=2000/5000, --forceCodeBlockToJettisonDueToOldAge=1 --useEagerCodeBlockJettisonTiming=1, --useBaselineJITCodeSharing=0, --useDFGJIT=0, --useFTLJIT=0, --useJIT=0.

Caveats

  • LinkBuffer statistics are cumulative allocations (jettisoned code included); pool RSS is the live figure.
  • Scores on this VM vary by ±10% run to run; they are shown only to flag gross regressions.
  • Retained-metadata counts are summed over all compilations of a run (some CodeBlocks were later jettisoned), i.e. they are the peak-ish population, not the end-of-run live set.
  • Machine-code sizes are x86_64; ARM64 code is generally 10-30% larger for the same sequences.

ビルド

4 vCPU の Linux VM 上で cmake -DPORT=JSCOnly -DCMAKE_BUILD_TYPE=Release -DDEVELOPER_MODE=ON -DENABLE_STATIC_JSC=ON、clang 18（16 分）。2 つ目のビルドでは -DENABLE_METADATA_STATISTICS=1（bytecode/UnlinkedMetadataTable.cpp のカウンタは upstream に存在するがオプションに接続されておらず、atexit で自己報告する）と、コンパイルごとの保持構造を数える 40 行の環境変数ゲート付き dataLog を DFG::Plan::finalizeInThread に追加した（付録にパッチ。ツリーからは戻し済み）。

静的サイズ

実ヘッダをインクルードする翻訳単位で約 115 型の sizeof を出力し、-Xclang -fdump-record-layouts でフィールドオフセットとパディングを得た（本レポートのサイズはすべて x86_64。36 bit アドレスの Apple arm64 ではいくつかの CompactPtr フィールドが縮む）。

ワークロード

JetStream2 のサブテストを RAMification モードの JetStream ドライバ経由で jsc シェル上で 1 つずつ実行（typescript, acorn-wtb, Babylon, pdfjs, gbemu, Air, octane-zlib, ML, raytrace, splay）し、加えて 1-4K 関数の合成ワークロード。各実行後に $vm.gc() を 2 回、$vm.linkBufferStats()（LinkBuffer プロファイルごとの累積リンク済みバイト: Baseline/DFG/FTL/OSR exit/IC スタブ/サンク）、memoryUsageStatistics()（ヒープサイズ、クラス別セル数）、MemoryFootprint()、そしてシェルが readline() でブロックしている間に Python ドライバが /proc/&lt;pid&gt;/smaps を読んで得た固定 1 GB 実行プールの RSS（連続する匿名 rwxp VMA の合計）。構成: default、--thresholdForJITAfterWarmUp=2000/5000、--forceCodeBlockToJettisonDueToOldAge=1 --useEagerCodeBlockJettisonTiming=1、--useBaselineJITCodeSharing=0、--useDFGJIT=0、--useFTLJIT=0、--useJIT=0。

注意点

  • LinkBuffer 統計は累積の割り当て量（jettison 済みコードを含む）。プール RSS が生存量。
  • この VM ではスコアが実行ごとに ±10% ばらつく。大きな後退を検出する目的でのみ示す。
  • 保持メタデータの計数は実行中の全コンパイルの合計（後に jettison された CodeBlock も含む）。すなわちピークに近い母集団であり、実行終了時の生存集合ではない。
  • 機械語サイズは x86_64。ARM64 は同じ列でも一般に 10-30% 大きい。

Deep dive: how the JIT tiers own memory深掘り: JIT ティアとメモリ所有関係

Tiers and who owns the code

UnlinkedCodeBlock (shared per source)
  • bytecode stream, UnlinkedMetadataTable (+ first linked buffer)
  • m_unlinkedBaselineCode: shared BaselineJITCode = machine code + JITCodeMap + unlinked IC/call descriptors + math IC bags
  • LLInt tier-up counter, arith profiles, unlinked value/array profiles
CodeBlock (per realm, per tier)
  • 216 B cell (224 B slot); MetadataTable copy (16 B/ValueProfile + per-op metadata)
  • BaselineJITData: one 112 B HandlerPropertyInlineCache per IC + constant pool
  • DFG::JITData: same handler ICs + m_exits (16 B/exit) + call link infos + watchpoints
DFG::JITCode / FTL::JITCode
  • CommonData: watchpoints, weak refs, code origins, inline call frames, IC/CLI bags
  • DFG: m_osrExit (80 B), event stream (14 B/event), minified graph
  • FTL: m_osrExit (80 B + reps), osrExitDescriptors (48 B + 9 B × frame operands), lazy slow paths, B3 byproducts
Executable pool (1 GB reserved on x86_64)
  • Baseline / DFG / FTL bodies, per-exit stubs, IC stubs (bespoke), thunks (per VM + process-wide)
  • 32 B granule, libpas size classes ≤ 2000 B, medium bitfit above

LLInt → Baseline. The LLInt counts on the shared UnlinkedCodeBlock counter (+5 entry / +10 return / +1 loop iteration; thresholdForJITAfterWarmUp = 500). Baseline compiles on the concurrent JITWorklist keyed by UnlinkedCodeBlock; JIT::link produces a BaselineJITCode that is cached on the unlinked block and reused by every later CodeBlock (useBaselineJITCodeSharing); the per-CodeBlock part is only BaselineJITData (handler ICs, 112 B each, allocated eagerly per unlinked IC). Property/call/scope/truthiness slow paths are per-VM or process-wide thunks; math ICs, compares and a few others still call C inline. Machine code per bytecode byte on x86_64 measured at 14.3 B (typescript).

Baseline → DFG → FTL. The DFG is gated by bytecode cost (maximumOptimizationCandidateBytecodeCost = 100000), thresholds scaled by cost, and thresholdForOptimizeAfterWarmUp = 1000; the FTL at thresholdForFTLOptimizeAfterWarmUp = 64000 and cost ≤ 60000. Compile-time memory (Graph, ~104 B DFG::Nodes individually malloc'd, 32 B AbstractValues ×(2 per node + 3 per block), B3 Value 40 B, Air Inst 64 B) is stack-scoped to Plan::compileInThreadImpl and freed; what stays is DFG::JITCode/FTL::JITCode plus the CodeBlock's JITData. Up to 2-3 plans are compiling concurrently (numberOfDFGCompilerThreads, numberOfFTLCompilerThreads). OSR exits are compiled lazily on first hit; the DFG reconstructs value recoveries from the event stream, the FTL reads a per-exit dense descriptor.

Inline caches. StructureStubInfo became PropertyInlineCache (96 B base) with HandlerPropertyInlineCache (Baseline/DFG, 112 B: data-driven chain of InlineCacheHandlers, each 128 B) and RepatchingPropertyInlineCache (FTL, 144 B, code patching + PolymorphicAccess). Handler code comes from ~99 pre-compiled thunks or bespoke stubs shared through SharedJITStubSet; each handler references a PolymorphicAccessJITStubRoutine (96 B) that owns cases, weak structures, a WatchpointSet and a Bag of clearing watchpoints (112 B/node). Calls use DataOnlyCallLinkInfo (80 B) embedded in bytecode metadata for LLInt+Baseline and OptimizingCallLinkInfo (96 B) in DFG/FTL; polymorphic calls are shared thunks over a CallSlot array (32 B each).

Metadata table. One linked MetadataTable per CodeBlock: [ValueProfile × N][LinkingData 16][offset16 table 104 (+offset32 208)][per-op metadata]; the first link reuses the unlinked buffer, later realms copy. 50 opcodes carry metadata (sizes in the table below); DFG/FTL CodeBlocks share the Baseline table but deep-copy constants/decls/exprs. Arith profiles (2 B) live in the unlinked block; value profiles are 16 B linked + 8 B unlinked.

Existing memory-saving mechanisms (do not re-propose)

  • Unlinked Baseline code sharing across CodeBlocks/realms; static shared LLInt entry stubs; process-wide VM-independent thunks and handler-IC thunks; SharedJITStubSet for stateless/bespoke stubs; polymorphic call thunks over data slots.
  • Metadata: 16-bit offset table (32-bit only above 64 KB), value profiles packed into a prefix, MetadataTable shared between tiers, arith profiles/LLInt counter on the unlinked block, RareData on both CodeBlock kinds, lazy catch/lazy-value-profile buffers, compressed ExpressionInfo, static_assert(sizeof(CodeBlock) <= 224).
  • DFG/FTL: lazy OSR-exit compilation with per-exit caching, no per-exit recoveries in DFG (event stream), FixedVectors + shrinkToFit at finalize, packed CodeOrigin/ValueRecovery/VariableEvent/ExitValue, PCToCodeOriginMap only when profiling, Graph/B3 freed after compile, jettison on exit counts and old age, gating by bytecode cost.
  • Executable memory: branch compaction + shrink on ARM64, exact-size allocation on x86_64, libpas page sharing/decommit, deleteAllCode on memory warnings, unlinked-code-block jettison in mini mode.
  • GC/object model: thin InlineWatchpointSet (1 word until first add), vtable-free Watchpoint + PackedCellPtr owners, DFG weak references as WriteBarrier/StructureID arrays (no Weak<> handles), single-slot transition tables, lazily created StructureRareData (≤ 96 B), GC-time dropping of unpinned PropertyTables, IsoSubspace lower-tier precise cells.

  • DFG::JITData: 同じハンドラ IC + m_exits（16 B/exit）+ call link info + ウォッチポイント

LLInt → Baseline。LLInt は共有 UnlinkedCodeBlock のカウンタで数える（入口 +5 / return +10 / ループ 1 反復 +1、thresholdForJITAfterWarmUp = 500）。Baseline は UnlinkedCodeBlock をキーとする並行 JITWorklist でコンパイルされ、JIT::link が生成する BaselineJITCode は unlinked 側にキャッシュされ以後の全 CodeBlock で再利用される（useBaselineJITCodeSharing）。CodeBlock ごとの部分は BaselineJITData（unlinked IC ごとに 112 B のハンドラ IC を先行確保）だけ。プロパティ/呼び出し/スコープ/truthiness のスローパスは VM ごと・プロセス共通のサンクだが、math IC や比較などはまだインラインで C を呼ぶ。x86_64 のバイトコード 1 B あたり機械語は 14.3 B（typescript 実測）。

Baseline → DFG → FTL。DFG はバイトコードコスト（maximumOptimizationCandidateBytecodeCost = 100000）でゲートされ、閾値はコストで補正、thresholdForOptimizeAfterWarmUp = 1000。FTL は thresholdForFTLOptimizeAfterWarmUp = 64000 かつコスト ≤ 60000。コンパイル時メモリ（Graph、個別 malloc の約 104 B DFG::Node、32 B AbstractValue ×（ノードごと 2 + ブロックごと 3）、B3 Value 40 B、Air Inst 64 B）は Plan::compileInThreadImpl のスタックスコープで解放され、残るのは DFG::JITCode/FTL::JITCode と CodeBlock の JITData。同時に 2-3 プランがコンパイル中になり得る（numberOfDFGCompilerThreads、numberOfFTLCompilerThreads）。OSR exit は初回発火時に遅延コンパイルされ、DFG はイベントストリームから復元情報を再構成し、FTL は exit ごとの密な記述子を読む。

インラインキャッシュ。StructureStubInfo は PropertyInlineCache（96 B 基底）となり、HandlerPropertyInlineCache（Baseline/DFG、112 B: 各 128 B の InlineCacheHandler をデータ駆動で連鎖）と RepatchingPropertyInlineCache（FTL、144 B、コードパッチ + PolymorphicAccess）がある。ハンドラコードは約 99 個の事前コンパイル済みサンクか SharedJITStubSet 経由で共有される個別スタブ。各ハンドラは case、弱 structure、WatchpointSet、クリア用ウォッチポイントの Bag（112 B/ノード）を持つ PolymorphicAccessJITStubRoutine（96 B）を参照する。呼び出しは LLInt+Baseline ではバイトコードメタデータに埋め込まれた DataOnlyCallLinkInfo（80 B）、DFG/FTL では OptimizingCallLinkInfo（96 B）。ポリモーフィック呼び出しは CallSlot 配列（各 32 B）上の共有サンク。

メタデータ表。CodeBlock ごとに 1 つのリンク済み MetadataTable: [ValueProfile × N][LinkingData 16][offset16 表 104 (+offset32 208)][op ごとのメタデータ]。最初のリンクは unlinked バッファを再利用し、以降の realm はコピーする。50 opcode がメタデータを持つ（サイズは下表）。DFG/FTL の CodeBlock は Baseline の表を共有するが、定数/decl/expr は深いコピー。算術プロファイル（2 B）は unlinked 側、value profile はリンク済み 16 B + unlinked 8 B。

既存の削減機構（再提案しない）

  • CodeBlock/realm 横断の unlinked Baseline コード共有。静的共有の LLInt エントリスタブ。プロセス共通の VM 非依存サンクとハンドラ IC サンク。stateless/個別スタブ用の SharedJITStubSet。データスロット上のポリモーフィック呼び出しサンク。
  • メタデータ: 16 bit オフセット表（64 KB 超のみ 32 bit）、前置領域にパックされた value profile、ティア間で共有される MetadataTable、unlinked 側の算術プロファイル/LLInt カウンタ、両 CodeBlock 種の RareData、遅延の catch/lazy value profile バッファ、圧縮 ExpressionInfo、static_assert(sizeof(CodeBlock) <= 224)。
  • DFG/FTL: exit ごとにキャッシュする遅延 OSR exit コンパイル、DFG では exit ごとの recovery を持たない（イベントストリーム）、finalize 時の FixedVector + shrinkToFit、パックされた CodeOrigin/ValueRecovery/VariableEvent/ExitValue、プロファイル時のみの PCToCodeOriginMap、コンパイル後の Graph/B3 解放、exit 回数と老化による jettison、バイトコードコストによるゲート。
  • 実行メモリ: ARM64 の分岐圧縮 + shrink、x86_64 の正確サイズ割り当て、libpas のページ共有/decommit、メモリ警告時の deleteAllCode、mini モードでの unlinked code block jettison。
  • GC/オブジェクトモデル: 薄い InlineWatchpointSet（初回 add まで 1 語）、vtable なしの Watchpoint + PackedCellPtr owner、DFG 弱参照は WriteBarrier/StructureID 配列（Weak<> ハンドル不使用）、単一スロット遷移表、遅延生成の StructureRareData（≤ 96 B）、GC 時の未ピン PropertyTable 破棄、IsoSubspace の lower-tier precise セル。

Object model & GC facts the JIT depends onJIT が依拠するオブジェクトモデルと GC

Facts the JIT bakes into code: the 8-byte JSCell header (StructureID 32-bit + indexingType/type/flags/cellState; runtime/JSCell.h:293-300); StructureID decodes as base + 32-bit offset because all Structures live in a 4 GB-aligned reservation (heap/StructureAlignedMemoryAllocator.cpp:106-121) — this is why so much JIT metadata can hold 4-byte WriteBarrierStructureIDs instead of pointers; JSObject = header + butterfly pointer, default inline capacity 6, out-of-line offsets ≥ 64; Structure = 112 B (fields read by generated code: prototype, classInfo, outOfLineTypeFlags, indexingMode, propertyTable, inlineCapacity, previousOrRareData, bitField, propertyHash, seenProperties; fields used only by C++: m_cachedPrototypeChain, m_transitionTable, m_transitionPropertyName, m_transitionWatchpointSet), StructureRareData = 96 B (created by ICs via startWatchingPropertyForReplacements on every prototype-chain hit), FunctionRareData = 72 B (80 B cell; the ObjectAllocationProfile the JIT reads for new F).

GC interplay: CodeBlock::visitChildren reports metadata size and non-shared JIT code as extra memory (so N realms over-count shared Baseline code N× while cache-only code counts 0×, and no DFG/FTL side tables are reported at all — CodeBlock.cpp:1213-1219); liveness of optimized code goes through shouldVisitStrongly → shouldJettisonDueToOldAge with 5/15/20/60 s TTLs; DFG code registers 24 B CodeBlockJettisoningWatchpoints in every watched set (inflating each Structure's thin transition set to a 24 B WatchpointSet), and stub routines are freed by Heap::deleteUnmarkedCompiledCode. Weak references from the JIT are arrays of WriteBarrier/StructureID reconciled at GC end, not Weak<> handles (24 B WeakImpl each), which is why the WeakBlock cost is dominated by transition maps and VM string maps, not by JIT metadata.

JIT がコードに焼き込む事実: 8 B の JSCell ヘッダ（32 bit の StructureID + indexingType/type/flags/cellState、runtime/JSCell.h:293-300）。StructureID は全 Structure が 4 GB 境界の予約領域に置かれる（heap/StructureAlignedMemoryAllocator.cpp:106-121）ため base + 32 bit オフセット で復号でき、多くの JIT メタデータがポインタの代わりに 4 B の WriteBarrierStructureID を持てる理由になっている。JSObject = ヘッダ + butterfly ポインタ、既定インライン容量 6、アウトオブラインオフセット ≥ 64。Structure = 112 B（生成コードが読むフィールド: prototype、classInfo、outOfLineTypeFlags、indexingMode、propertyTable、inlineCapacity、previousOrRareData、bitField、propertyHash、seenProperties。C++ だけが使うフィールド: m_cachedPrototypeChain、m_transitionTable、m_transitionPropertyName、m_transitionWatchpointSet）。StructureRareData = 96 B（IC がプロトタイプチェーンヒットのたびに startWatchingPropertyForReplacements で生成）。FunctionRareData = 72 B（80 B セル。JIT が new F で読む ObjectAllocationProfile）。

GC との相互作用: CodeBlock::visitChildren はメタデータサイズと非共有 JIT コードを extra memory として報告する（そのため N realm では共有 Baseline コードが N 倍に数えられ、キャッシュ専用コードは 0 倍、DFG/FTL の補助表は一切報告されない — CodeBlock.cpp:1213-1219）。最適化コードの生存判定は shouldVisitStrongly → shouldJettisonDueToOldAge（TTL 5/15/20/60 s）。DFG コードは監視する各集合に 24 B の CodeBlockJettisoningWatchpoint を登録し（各 Structure の薄い遷移集合を 24 B の WatchpointSet に膨らませる）、スタブルーチンは Heap::deleteUnmarkedCompiledCode で解放される。JIT からの弱参照は GC 終了時に照合される WriteBarrier/StructureID 配列であり Weak<> ハンドル（各 24 B の WeakImpl）ではないため、WeakBlock のコストは JIT メタデータではなく遷移マップや VM の文字列マップに支配される。

Evidence (source)根拠（ソース）

thresholdForJITAfterWarmUp = 500, thresholdForJITSoon = 100 (runtime/OptionsList.h:355-356) are applied on the shared LLInt counter with no scaling by bytecode size or code type; the LLInt adds 5 on entry, 10 on return and 1 per loop iteration (llint/LowLevelInterpreter.asm, LowLevelInterpreter64.asm). Proposal提案

Scale the LLInt threshold by bytecode cost (reuse the DFG curve or a simple bytecodeCost / K), give Program/Module code a multiplier (today only eval has evalThresholdMultiplier), and add a hard cap: functions above the DFG candidacy limit only get Baseline via loop OSR after a much larger count.
