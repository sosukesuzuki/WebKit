FTL・B3・Air コンパイル時間監査

JavaScriptCore の FTL・B3・Air バックエンドで最適化ティアのコンパイル時間とコンパイラのメモリを削減できる 20 件の機会を、HEAD c73014505a のコードで検証したうえで計測用ビルドで実測した。うち 8 件を実装し、FTL の B3+Air 時間を 4.8%、OMG の時間を 3.1% 削減した。

要点

  • FTL コンパイル 1,283 件（JetStream2 サブセット）の実測：FTL が生成する定数の 74% が重複、メモリアクセスの 70% が Const+Add アドレスを持ち、Air は実際に使う Inst ストレージの 3.2 倍を確保している。
  • 8 件の修正をブランチに投入：FTL の B3+Air 時間 −4.8%（n=11 対 13、σ≈2.5%）、B3 −6.1%、reduceStrength −8.1%、lowerToAir −12.8%、exit 引数構築 −14.3%；OMG（pglite、2,288 件）−3.1%。
  • メモリ：Air の Inst 確保 −69%、greedy の PhaseInsertionSet バッファ −97.5%、FTL の初期 B3 値 −19%、OMG が Air の間生かす B3 バイト −42%。
  • コード読解による見積もりのうち 2 つは実測で覆った：ノードごとの exit 状態キャッシュが効くのは exit の 19% だけ、OMG で未参照の値だけ解放しても回収できるのは 20〜40% ではなく 9%（Origin ごとの代表値が必要だった）。
  • WTF の潜在バグが表面化：インライン容量付きの Deque<T, N> は move でインライン要素を失うため、提案した Deque<Interval, 4> はクラッシュし取り下げた。

対象範囲と手法

本監査が扱うのはコンパイラ側のコスト、すなわちコンパイルスレッドの実時間とコンパイラが確保するメモリのみである。対象は JavaScriptCore の3つの最適化バックエンド、ftl/（DFG→B3 lowering と OSR exit 機構）、b3/（SSA ミドルエンド）、b3/air/（機械語レベル IR、レジスタアロケータ、コードジェネレータ）である。生成コードの品質は、提案が影響し得る場合を除いて対象外とする。

作業は sosukesuzuki/WebKit のコミット c73014505a のソースを読むことで行った。10人のアナリストがそれぞれコードの一区画（B3 データ構造、ReduceStrength、その他の B3 フェーズ、B3→Air lowering、Air データ構造、greedy アロケータ、残りの Air フェーズ、FTL lowering、FTL exit と JIT コード、横断的基盤）を担当した。彼らが出した候補はすべて、2人の敵対的レビュアー（1人は HEAD に対する事実関係と陳腐化の確認、もう1人は現実的な効果と実現可能性の評価）が独立に再検証し、最後に「網羅性批評者」が誰も扱っていない領域を探した。合計 84 件の候補が生成され、84 件すべてが事実確認を通過した。多くは2〜3人のアナリストが独立に発見しており、有用なクロスチェックになっている。上位 20 件を以下に詳述し、残りは付録にまとめる。

本書の初版はコード読解のみに基づいていた。その後、実際のビルドで検証した。同じコミットから JavaScriptCore をリリース構成でビルドし（JSCOnly ポート、clang 18、x86_64、4 vCPU）、JSC_reportTotalPhaseTimes=1 でプロファイルし、約 80 個のプロセス全体カウンタを仕込んで各知見の数値を裏付けまたは反証した。そのうえで 8 件の修正を実装し、対照ビルドと比較計測した（次節）。以下で「実測」とある数値はそのビルド由来であり、それ以外のサイズ見積もりは引き続き構造体レイアウトから導いたものである。もう一点、このコードベースには既に多くのコンパイル時間改善が施されている。B3::Value は 40 バイトのヘッダに子をインライン格納し、Air::Inst はちょうど 64 バイトで 3 つの引数をインラインに持ち、ReduceStrength は既定でシングルパス、LowerToAir はハッシュマップでなくインデックスマップを使い、greedy アロケータは複数の解析を1回の走査に融合している。以下の知見は、それらの対策を差し引いた後に残るものである。

計測結果

結論：20 件のうち 8 件をブランチに実装し、実ワークロードで FTL バックエンド（B3 + Air）を約 5%、OMG バックエンドを約 3% 短縮した。同時に Air の命令ストレージ確保の 3 分の 2 と、OMG がレジスタ割り付けの間生かしている B3 メモリの 42% を削減した。残りの知見の大半はカウンタで機構を確認でき、3 件はコード読解の見積もりより小さいことが分かった。

WTF の潜在バグ：インライン容量付き Deque

知見 4 の最初の試みは Deque<Interval> を Deque<Interval, 4> に置き換えたが、greedy アロケータの setStageAndEnqueue で CrashOnOverflow によりクラッシュした。原因は WTF にある。Deque<T, inlineCapacity>::swap（move コンストラクタと move 代入が使う）は m_buffer.swap(other.m_buffer, 0, 0) を呼ぶ（WTF/wtf/Deque.h:399–410）ため、インライン要素が交換されない。インラインバッファを持つ Deque は、それを含むオブジェクトが move されると内容を黙って失う——TmpMap<TmpData> は成長のたびにそれを行う。ツリー内に非ゼロのインライン容量を持つ Deque を move するコードは現在ないため、気付かれずにいた。したがって LiveRange の変更には知見 4 で述べた Vector<Interval, 2> ＋逆順構築の案が必要であり、Deque::swap は修正するか inlineCapacity == 0 を static_assert すべきである。

パイプラインのどこにコストが集中するか

最適化パイプラインは固定されたフェーズ列である（b3/B3Generate.cpp の generateToAir()、続いて b3/air/AirGenerate.cpp の prepareForGeneration()）。図は知見が集中するフェーズを示す。コストの大半は3つの構造的事実に由来する。FTL フロントエンドが必要以上の B3 値を生成するため、初期の B3 フェーズはすべて膨らんだグラフを走査すること。複数の B3 フェーズが無効化のたびに同じ CFG 解析（predecessor、dominator、natural loop）を再構築すること。そして単独で最も高価なフェーズである Air レジスタアロケータが、大きな関数では固定費が支配的になる Tmp ごと・ブロックごとのサイドテーブルを抱えていることである。

フラグを分離する：m_preserveB3Origins は「グラフ全体が生き残らねばならない」という意味でダンプ／逆アセンブラのパスに残し、「PC→Origin マップが必要」という条件を別に追加する。freeUnneededB3ValuesAfterLowering では、マップだけが必要な場合に (a) すべての Air Inst を1回走査して inst.origin->index() ごとにビットを立て、既存の Special 由来の保持集合と和をとり、残りを解放する——新しい Inst を生成するすべての Air フェーズは既存の Inst から origin をコピーする（AirBreakCriticalEdges.cpp:49、AirLowerAfterRegAlloc.cpp:165/231/263、AirAllocateRegistersByGreedy.cpp:3226 ほかの挿入箇所で確認済み）ため構造的に安全である。あるいは (b) さらに進めて、保持されない origin を一意な Origin ごとのスタブ Nop 値（HashMap<Origin bits, Value*> で重複排除）に付け替え、保持量を B3 値数ではなく wasm opcode の種類数に比例させる。

中〜低：保持されない origin を参照する Air コードがあれば use-after-free になるが、参照箇所の集合は小さく、既存の保持ロジックが既に列挙している。スイープ前後で m_values.size() をログし、JSC_useConcurrentJIT=0 で大きなモジュールを OMG コンパイルしながらピーク RSS／malloc 高水位を比較して計測する。

Air::Inst、Arg、Tmp に VectorTraits がない。 Inst はユーザー定義の move とデストラクタ、Arg と Tmp はユーザー定義の既定コンストラクタを持つため canMoveWithMemcpy が false となり、すべての Vector 成長、removeAllMatching 圧縮（DCE、スタックアロケータ、assignRegisters）、removeAt が要素を1つずつ分岐と可変長 memcpy で移動する。3 つとも自明に再配置可能である（out-of-line の引数ポインタは一意に所有される）。3 行の template<> struct VectorTraits<JSC::B3::Air::Inst> : VectorTraitsBase<false, void> { static constexpr bool canMoveWithMemcpy = true; };（Arg/Tmp にも同様、または Arg のコンストラクタを = default にする）でそれらが一括 memcpy になる。あるレビュアーは executeInsertions が独自のシフトループを持ち恩恵を受けないと指摘する。Air 時間の約 1%、リスクなし。

推奨する着手順序と計測方法

小さく生成コードに影響しない項目は上記のとおり投入・計測済みである（10、5、6、12、19 の VectorTraits の半分、15、1 の第 1 段階、3 の定数の半分、2）。残りを計測結果が示す順に挙げると：知見 3 のオフセット畳み込みの半分（最大 16 万値を追加削減でき、B3 側で最大の残された手段）；CSE の唯一保持者プレフィルタ（9、探索ブロックの JS で 35%、OMG で 68% をカバー）；Deque の近道が危険と分かった今、Vector<Interval, 2> 版の LiveRange（4）；1 回の実行で 63〜157 MB の一時メモリを使う liveness Actions のレイアウト（7）；コンパイル 1 件あたり 830 回の CheckSpecial hiddenBranch() 実体化（13）；CSE のループ再走査（8）；残りの LowerToAir 整理（19）。Dominators のレイアウト（16）、duplicateTails（11）、スピルラウンドの走査（18）はそれぞれ 1〜4% と実測され、後回しでよい。

ここで使った計装は再利用できる。カウンタのパッチとスクリプトは jsc-compile-time-audit/measurements/ にある。既存の計装でその大半は十分である。JSC_logPhaseTimes=1 と JSC_reportTotalPhaseTimes=1 はすべての CompilerTimingScope を報告し、B3 と Air のすべての PhaseScope はその1つである。greedy アロケータには既に buildLiveRanges と allocateRegisters のスコープがあり、Air の liveness にも独自のスコープがある。JSC_dumpB3GraphAtEachPhase=1 と JSC_dumpAirGraphAtEachPhase=1 はフェーズごとの値数と命令数を与える。まず埋めるべき穴は 2 つあり、ブランチ上で埋めた：FTL::lowerDFGToB3 と buildExitArguments を囲む CompilerTimingScope の追加（それまで FTL lowering は DFG 時間に帰属していた、dfg/DFGPlan.cpp:474–477）。まだ欠けているのはコンパイルごとの確保カウンタ（malloc インターポーザ、または prepareForGeneration 前後の fastMallocStatistics の差分）の追加で、メモリの知見を見積もりではなく定量化できるようにする。コンパイルスレッドが計測対象になるよう JSC_useConcurrentJIT=0 で、FTL の多い JavaScript ワークロードと、OMG 固有の項目（2、10、15）向けの大きな wasm モジュールで、すべてを実行する。
