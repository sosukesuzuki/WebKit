FTL·B3·Air Compile-Time Audit

Twenty verified opportunities to cut optimizing-tier compile time and compiler memory in JavaScriptCore's FTL, B3 and Air backends, ranked by expected payoff, with file-and-line evidence at HEAD c73014505a.

Key takeaways

  • Every FTL speculation check copies and re-prunes the whole OSR availability map and retains a full-width exit descriptor (9 bytes × frame slots) for the life of the code.
  • Every Wasm OMG compile keeps the entire B3 value graph alive through register allocation just to read one 8-byte Origin per instruction.
  • FTL hands B3 an IR that is roughly 30–50% larger than necessary: one constant per use and a Const+Add+Load triple per field access, both already solved in the Wasm OMG generator.
  • The greedy register allocator pays ~150 bytes of heap per Tmp and 656 bytes per basic block up front, and bubble-sorts concatenated spill runs.
  • Several B3 phases do full-procedure work that a one-line guard would skip: fixSSA on OMG, duplicateTails' unconditional CFG invalidation, CSE's second sweep over every loop block.

Scope and method

This audit looks only at compiler cost — wall-clock time on the compilation thread and memory allocated by the compiler — in the three optimizing backends of JavaScriptCore: ftl/ (DFG→B3 lowering and OSR-exit machinery), b3/ (the SSA middle end) and b3/air/ (the machine-level IR, register allocator and code generator). Generated-code quality is out of scope except where a proposal might affect it.

The work was done by reading the source at commit c73014505a of sosukesuzuki/WebKit. Ten analysts each took a slice of the code (B3 data structures, ReduceStrength, the other B3 phases, B3→Air lowering, Air data structures, the greedy allocator, the remaining Air phases, FTL lowering, FTL exits and JIT code, and cross-cutting infrastructure). Every candidate they produced was then independently re-checked by two adversarial reviewers — one for factual correctness and staleness against HEAD, one for realistic impact and feasibility — and a final "completeness critic" looked for areas nobody had covered. In total 84 candidate findings were produced and all 84 survived fact-checking; many were found independently by two or three analysts, which is a useful cross-check. The top twenty are presented in full below; the rest are summarized in the appendix.

Two caveats. First, nothing here was measured: no build of WebKit was available, so all sizes are derived from struct field lists and all time estimates from loop structure and typical FTL/OMG procedure shapes (thousands to tens of thousands of B3 values, hundreds to thousands of blocks, tens of thousands of Air Tmps). Each finding states how to measure it. Second, this code base has already had a great deal of compile-time work: B3::Value stores its children inline with a 40-byte header, Air::Inst is exactly 64 bytes with three inline args, ReduceStrength is single-pass by default, LowerToAir uses index maps rather than hash maps, and the greedy allocator fuses several analyses into one walk. The findings below are what remains after accounting for those mitigations.

Where the pipeline spends its effort

The optimizing pipeline is a fixed sequence of phases (b3/B3Generate.cpp generateToAir(), then b3/air/AirGenerate.cpp prepareForGeneration()). The figure marks the phases where the findings concentrate. Three structural facts drive most of the cost: the FTL front end emits more B3 values than it needs to, so every early B3 phase walks a bloated graph; several B3 phases rebuild the same CFG analyses (predecessors, dominators, natural loops) after invalidation; and the Air register allocator — the single most expensive phase — carries per-Tmp and per-block side tables whose fixed costs dominate on large functions.

FTL lowering and OSR-exit metadata

1. Every speculation check re-captures the full OSR exit state and retains a full-width descriptor

bothFTLimpact: medium · memory high on exit-heavy codeeffort: M

What happens today

Each call to speculate() / blessSpeculation() (ftl/FTLLowerDFGToB3.cpp:27177–27195) allocates a new OSRExitDescriptor through appendOSRExitDescriptor (:27108–27132) whose FixedOperands<ExitValue> m_values has one slot per argument, local and tmp of the whole inlined frame stack (ExitValue is a 1-byte kind plus a packed 8-byte union, 9 bytes). It then calls buildExitArguments (:27244–27313), which:

AvailabilityMap availabilityMap = this->availabilityMap();   // copy #1: Vector<Availability> (16 B × L)
availabilityMap.pruneByLiveness(m_graph, exitOrigin);        // copy #2 + bytecode liveness walk
...
for (unsigned i = 0; i < exitDescriptor->m_values.size(); ++i) {
    ...
    ExitValue exitValue = exitValueForAvailability(arguments, map, availability); // up to 7 HashMap probes
    exitDescriptor->m_values[i] = exitValue;
}

pruneByLiveness is *this = filterByLiveness(...) (dfg/DFGAvailabilityMap.cpp:75–78), and filterByLiveness allocates a second full-size Operands<Availability> and walks every inline frame's bytecode-liveness bit rows via Graph::forAllLiveInBytecode (dfg/DFGGraph.h:1121–1160). exitValueForNode (:27380–27406) probes up to seven separate HashMap<Node*, LoweredNodeValue> tables per node-backed operand. Finally the live values are appended one at a time into the check's Vector<Value*, 3> children.

Why it costs

For a frame with L operand slots, every check costs three heap allocations (two 16·L-byte availability copies and a 9·L-byte descriptor), an O(L + inline depth) liveness walk, an O(L) availability scan and an O(L · probes) value-resolution loop. Nothing in this depends on state that changes between checks emitted for the same DFG node: the availability map is only mutated in compileBlock (:526) and at the end of compileNode (:2092), and exitOrigin is constant for the node. Typical nodes emit two to four checks (an Int32 GetByVal emits cell, index, bounds and hole checks). The reviewers noted one subtlety: the resolved exit values can legitimately differ between checks of one node, because lowInt32/lowJSValue register new representations mid-node, so only the pruned availability and the materialization map are bit-identical; the value resolution needs a generation counter on the lowered-value maps to be cacheable.

The retained side is larger than the transient side. Every descriptor lives in FTL::JITCode::osrExitDescriptors for the lifetime of the compiled code (ftl/FTLJITCode.h:86–90); shrinkToFit only trims capacity. With N checks and L slots that is N·(9L + 48) bytes: for N = 1000, L = 100, roughly 1 MB per compiled function, plausibly comparable to or larger than the machine code itself.

Proposal (staged)

(1) Replace the two-step copy with AvailabilityMap availabilityMap = this->availabilityMap().filterByLiveness(m_graph, exitOrigin); (make filterByLiveness const) — this mirrors DFGOSRAvailabilityAnalysisPhase.cpp:162 and removes one allocation per check with zero risk. (2) Keep a one-entry cache of "operands live in bytecode at exitOrigin" (a FastBitVector keyed on the full CodeOrigin) plus a reusable scratch Operands<Availability> member, filled in place; consecutive checks almost always share the origin. (3) Add a per-node cache keyed on (availability version bumped at :526/:2092, exitOrigin, a generation counter bumped by every set*() on the lowered-value maps) that stores the pruned availability, the materialization map and the resolved (operand, ExitValue, LValue) list; on a hit, only re-append the LValues. (4) Reserve capacity on the check's children vector before appendColdAnys. Descriptor sharing and compaction are covered in finding 20.

Risk and measurement

Low for stages 1–2 (liveness at a CodeOrigin is invariant during lowering). Medium for stage 3: the cache key must cover everything buildExitArguments reads; validate by recomputing and comparing under JSC_validateFTLOSRExitLiveness. To measure, note that today FTL lowering is attributed to "DFG" time because m_timeBeforeFTL is sampled after lowerDFGToB3 (dfg/DFGPlan.cpp:474–477, consumed at jit/JITPlan.cpp:294–295); add a CompilerTimingScope("FTL", "lowerDFGToB3") and a counter of descriptors versus distinct (node, origin) keys, and sum m_values.size() × 9 at shrinkToFit time.

3. FTL hands B3 an inflated graph: one constant per use, and Const+Add+Load per field access

bothFTL→B3impact: mediumeffort: S (constants) · M (offsets)

What happens today

Output::constInt32/constInt64/constDouble each append a brand-new constant value to the current block (ftl/FTLOutput.cpp:119–132); only the dozen values in FTLCommonValues are shared. FTLLowerDFGToB3.cpp has roughly 370 constInt32, 130 constInt64, 200 constIntPtr and 335 weakPointer call sites, plus one constant per vmCall (the operation pointer and the call-site index) and one per use of a DFG constant edge in lowInt32/lowJSValue. Separately, every field access goes through Output::address → addPtr(base, offset) → add(base, constIntPtr(offset)) (ftl/FTLOutput.h:286–305) and then Output::load/store build a MemoryValue with offset 0 (ftl/FTLOutput.cpp:429–469), so each of the roughly 600–800 m_out.load*/store*(…, m_heaps.X) sites emits three values — Const, Add, Load — where B3's MemoryValue constructors that take an offset (b3/B3MemoryValue.h:121–145) would allow one.

Why it costs

B3 does eventually reach the canonical form: ReduceStrength's Const case hashes every constant, clones the first non-root occurrence into the root block and replaces the original with an Identity (b3/B3ReduceStrength.cpp:3377–3396), and its Load rule folds Load(Add(x, c)) into an offset (:2645–2662). But each redundant value has already cost an arena allocation, a SparseCollection slot and a block-list slot at lowering time, one ValueKey hash and an in-place replacement in ReduceStrength, a revisit in ReduceStrength's second walk (finding 14), a performSubstitution fix-up in every user, and a DCE deletion. The extra Add/Const pairs additionally survive through reduceDoubleToFloat and are only removed by DCE. The reviewers' consensus is that redundant constants are 15–25% of initial FTL B3 values and that the Const+Add+Load shape inflates the initial graph by a further 30–50%, for a likely 2–5% of total FTL compile time and a proportional cut in peak B3 memory before DCE. The Wasm OMG generator already does both things right: it pools constants through m_constantPool (wasm/WasmOMGIRGenerator.cpp:1141, 1502–1516) and emits MemoryValues with direct offsets (:974, 1353, 2104).

Proposal

Constants: add an UncheckedKeyHashMap<B3::ValueKey, LValue> m_constantPool to FTL::Output, have constInt32/constInt64/constDouble/constFloat do ensure() and on a miss create the value in the prologue block (which dominates everything, including catch entrypoints via the EntrySwitch). Because the prologue already has a terminator by the time most constants are requested, insert with an InsertionSet at index 0 as OMG does. Drop the per-use result->setOrigin() calls in lowInt32/lowJSValue, since they would mutate a shared value. Offsets: give B3::TypedPointer an OffsetType m_offset, have Output::address fold field.offset() into it instead of emitting an Add, and have the load*/store* family pass pointer.offset() to the offset-taking MemoryValue constructors; the ~10 sites that take TypedPointer::value() for non-memory arithmetic need a materialization helper. legalizeMemoryOffsets already repairs offsets the ISA cannot encode.

Risk and measurement

Low: both shapes are exactly what B3 canonicalizes to, so generated code is unchanged; the only observable difference is the B3 origin attached to constants in dumps. Measure with JSC_dumpB3GraphAtEachPhase (value count entering reduceStrength(Initial)) and JSC_logPhaseTimes=1 / JSC_reportTotalPhaseTimes=1.

20. OSRExitDescriptors are retained forever and never compacted or shared

memoryFTLimpact: low–medium (retained)effort: M

What happens today

Descriptors live in a SegmentedVector<OSRExitDescriptor, 8> on FTL::JITCode (ftl/FTLJITCode.h:87–89) and are allocated eagerly at lowering time (finding 1), while the OSRExit objects that reference them are created lazily in prepareOSRExitHandle from the check's generator (ftl/FTLOSRExit.cpp:82–97). A check that B3 later turns into a Nop (b3/B3ReduceStrength.cpp:3210–3217) or that sits in a block B3 deletes leaves an orphan descriptor; exception-handler descriptors from preparePatchpointForExceptions (35 call sites) are per patchpoint inside a try region; and two checks with identical (format, profile, exit state) get separate descriptors. FTLCompile.cpp:231–236 then walks every descriptor × every operand to apply localsOffset.

Why it costs, proposal

Each descriptor retains 9·L + 48 bytes for the life of the code, with L the machine-frame operand count (union of all inlined frames). The reviewers rate the dead/duplicate fraction as modest for ordinary checks (FTL already elides statically unnecessary checks) but plausibly significant for exception-handler descriptors. Two complementary changes: store m_values sparsely (only non-ExitValueDead entries as (operandIndex, ExitValue) pairs, or a bitmap plus dense array); and after B3::generate, compact osrExitDescriptors to the set referenced by m_osrExit, lazy slow paths and exception handles. Pairs naturally with the per-node cache in finding 1, which makes descriptor sharing a by-product. Measure by logging descriptor count versus referenced count and total m_values bytes at shrinkToFit.

B3 phases

2. Wasm OMG keeps every B3 Value alive through the whole Air pipeline to read an 8-byte Origin per instruction

memoryB3 / Air / Wasmimpact: medium–high on OMG peakeffort: M

What happens today

B3Generate.cpp:149 calls Procedure::freeUnneededB3ValuesAfterLowering() right after lowerToAir so that the B3 graph is gone before register allocation, which is where Air memory peaks. That function returns before freeing anything when m_code->shouldPreserveB3Origins() is set (b3/B3Procedure.cpp:475–476). FTL sets that flag only for the sampling profiler or IR dumps (ftl/FTLState.cpp:75–76), but the Wasm OMG generator calls procedure.setNeedsPCToOriginMap() unconditionally (wasm/WasmOMGIRGenerator.cpp:6964), and that setter couples the two concepts:

void Procedure::setNeedsPCToOriginMap()
{
    m_needsPCToOriginMap = true;
    m_code->forcePreservationOfB3Origins();   // b3/B3Procedure.cpp:514-518
}

The only thing code generation reads from a preserved value is inst.origin->origin(), one Origin word per Air instruction (b3/air/AirGenerate.cpp:205–209; O0 path at AirAllocateRegistersAndStackAndGenerateCode.cpp:587–593), consumed by WasmCallee.cpp:503–535 to build the call-site-index map. Every other Air dereference of inst.origin is for Specials, CCall and WasmBoundsCheck — exactly the opcodes that freeUnneededB3ValuesAfterLowering already preserves (:478–503).

Why it costs

For every OMG and OSR-entry compile, the full B3 graph — values at 48 bytes and up, MemoryValues at 64–80, StackmapValues at 112 plus their heap m_reps, and the SparseCollection slot vector — stays allocated through all thirteen Air phases. For a 50k-value wasm function that is several megabytes sitting at the pipeline's peak, per concurrent compile thread; one reviewer estimated 20–40% of OMG peak compiler memory on large functions, another 5–10%, depending on how large the Air side is. Compile time is roughly neutral either way.

Proposal

Split the flag: keep m_preserveB3Origins meaning "the full graph must survive" for dump/disassembler paths, and add a separate "needs PC→Origin map" condition. In freeUnneededB3ValuesAfterLowering, when only the map is needed, either (a) walk every Air Inst once, set a bit per inst.origin->index(), union with the existing Special-driven preservation set, and free the rest — safe by construction because every Air phase that creates a new Inst copies its origin from an existing one (verified at AirBreakCriticalEdges.cpp:49, AirLowerAfterRegAlloc.cpp:165/231/263, AirAllocateRegistersByGreedy.cpp:3226 and the other insertion sites); or (b) go further and retarget non-preserved origins to one stub Nop value per distinct Origin (deduplicated through a HashMap<Origin bits, Value*>), so retention scales with the number of distinct wasm opcodes rather than B3 values.

Risk and measurement

Medium–low: any Air code that dereferenced a non-preserved origin would be a use-after-free, but the set of dereference sites is small and already enumerated by the existing preservation logic. Measure by logging m_values.size() before and after the sweep and comparing peak RSS / malloc high-water mark while OMG-compiling a large module with JSC_useConcurrentJIT=0.

8. CSE's loop re-sweep reprocesses every block of every natural loop

timeB3impact: mediumeffort: M

What happens today

After the main reverse-post-order sweep, eliminateCommonSubexpressions collects the header and every body block of every natural loop into an IndexSet and calls performCSE(&loopBlocks) a second time (b3/B3EliminateCommonSubexpressions.cpp:374–389). The comment explains why: in RPO the loop body has not been processed when the header is visited, so back-edge queries from the header miss matches that only appear once the body is summarized. The second pass runs the full process() pipeline on each block (:485–566): performSubstitution on every value, a ValueKey hash and linear match scan in PureCSE (which now also finds the value itself and skips it, b3/B3PureCSE.cpp:80–82), a rebuilt ImpureBlockData, and another backward search for every memory value.

Why it costs, proposal

In hot FTL and OMG functions nearly all code is inside some loop, so CSE does close to its entire job twice. Only queries whose first-pass walk actually reached a not-yet-processed block (one later in RPO, i.e. across a back edge) can gain from the re-sweep, and nothing records which those were. Proposal, in order of safety: record a per-value bit in findMemoryValue/findWasm* when the backward walk pops a block whose RPO index is at or after the querying block's, and in pass 2 skip the backward walks for values without the bit; or restrict pass 2 to the blocks that issued such queries. The reviewers caution that pass 2 also yields secondary pure-CSE gains when performSubstitution re-keys a value whose child load was eliminated in pass 1, so a conservative filter (re-sweep any block that issued a back-edge query, plus blocks it dominates within the loop) is preferable to a precise one. Validate by comparing eliminated-value counts on a benchmark corpus; measure with a CompilerTimingScope around each performCSE call.

9. CSE backward walks have no "anyone else holds this pointer" pre-filter and allocate a worklist per query

timeB3impact: low–mediumeffort: S

What happens today

findMemoryValue (b3/B3EliminateCommonSubexpressions.cpp:980–1035) checks the current block's memoryValuesAtTail, early-outs if the block has an overlapping write, then constructs a fresh BlockWorklist (a BitVector plus vector; a heap allocation once the procedure has more than 63 blocks) and walks predecessors until it finds a match, an overlapping write, or the root. A match requires another MemoryValue keyed by the same lastChild pointer. For a load whose address value is used by no other memory value — very common: unique address arithmetic, first touch of a field — the walk can never succeed and runs until a clobbering write or the root. The Wasm-struct path already recognizes this: it tallies holders per key in m_structKeyFilters during the summary pass and bails before walking when the querying value is the sole holder (:1108–1122, used at :1144, rationale at :1601–1605). The plain memory path and findWasmArrayValue (:1375–1416) do not.

Proposal

Mirror the struct filter for MemoryValue and array keys: an UncheckedKeyHashMap<Value*, {Value* first; unsigned count}> populated wherever memoryValuesAtTail.add() is called, and an isOnlyHolderOfPointer(ptr) check at the top of findMemoryValue. Replace the per-query BlockWorklist in findMemoryValue, findStoreAfterClobber, findWasm* and processWasmAddressValue with an epoch-stamped IndexMap<BasicBlock*, unsigned> plus a reusable stack owned by the CSE object (the pattern SSACalculator::computePhis already uses). One reviewer notes the walk is a DFS that aborts at the first clobbering block, so in call-heavy FTL code most walks already die quickly; the win is concentrated in call-free, load-heavy regions (OMG numeric and GC code, FTL array loops) and is doubled by the loop re-sweep in finding 8. CSE results are unchanged.

10. fixSSA's early-out tests SparseCollection::isEmpty(), which is false forever once any Variable was allocated

bothB3 (OMG)impact: medium on every OMG compileeffort: S

What happens today

fixSSA returns early when proc.variables().isEmpty() (b3/B3FixSSA.cpp:354, again at :366). But SparseCollection::isEmpty() is m_vector.isEmpty() (b3/B3SparseCollection.h:126), and remove() nulls the slot and pushes the index onto a free list without shrinking the vector (:74–79); packIndices() is only ever called on m_values. OMG creates one Variable per wasm local and argument, runs its own fixSSA before prepareForGeneration (wasm/WasmOMGIRGenerator.cpp:6999, 7005), and the DCE inside reduceStrength(Initial) then deletes every variable (b3/B3EliminateDeadCode.cpp:96–100). When the pipeline's own fixSSA runs (B3Generate.cpp), the collection is all holes but not "empty".

Why it costs, proposal

Every OMG compile therefore pays fixSSALocally (a full value walk with performSubstitution), two killDeadVariables walks, a breakCriticalEdges scan, a VariableLiveness whose dense matrices are sized blocks × ⌈N/64⌉ words × 4 (up to the 4 MB-per-matrix budget, zero-filled), an SSACalculator with dominance frontiers, and the conversion walk — for a guaranteed no-op. The fix needs no new state: SparseCollection already tracks holes, so bool isEmpty() const { return m_vector.size() == m_indexFreeList.size(); } makes both early-outs effective; alternatively have killDeadVariables report survivors. Additionally, since duplicateTails is the only in-pipeline producer of Variables, B3Generate.cpp could skip fixSSA when it demoted nothing (see finding 11). FTL never creates Variables, so this is OMG-specific. Measure with JSC_logPhaseTimes=1: the fixSSA, VariableLiveness and fixSSA: computePhis/convert scopes should vanish for the second run.

11. duplicateTails demotes values from every candidate block and unconditionally invalidates the CFG

bothB3impact: low–mediumeffort: S

What happens today

Candidates are all blocks with ≤3 values, ≤3 successors and a Void terminal (b3/B3DuplicateTails.cpp:71–89, maxB3TailDupBlockSize = 3). valuesToDemote then includes every Phi in a candidate and every value defined in a candidate and used elsewhere (:93–103), and demoteValues runs on all of them before the phase decides what to clone. Cloning only happens for blocks ending in Jump to a candidate (:110–143). Candidates reached only through Branch/Switch edges — the ubiquitous FTL shape x = Load(…); Branch(x) sitting behind another branch — are never duplicated, yet their exported values are turned into Variable + Set + Get per use. Finally the phase calls m_proc.resetReachability(); m_proc.invalidateCFG(); unconditionally (:146–147), even when it cloned nothing.

Why it costs, proposal

Unneeded demotion creates Variables and values that are torn down again, and it forces the pipeline's fixSSA (finding 10) to run its full machinery: VariableLiveness matrices, SSACalculator, dominance frontiers, only to replace each Get with the original dominating value. The unconditional invalidation discards the memoized Dominators and triggers a predecessor recomputation (finding 15) on every optLevel-2 compile. Proposal: run the clone loop twice — a side-effect-free pass that records (block, tail) pairs while mirroring candidates.remove(block) (the only mutable state it depends on), then build valuesToDemote only from recorded tails, call demoteValues only if non-empty, perform the recorded clones, and return a bool changed so that resetReachability()/invalidateCFG() and the downstream fixSSA run only when something was cloned. Generated code is unchanged because non-duplicated tails never needed demotion. Measure with JSC_logPhaseTimes=1 on duplicateTails and fixSSA, and by counting proc.variables().size() after the phase.

14. ReduceStrength escalates to a full second walk whenever any CFG or SSA cleanup changed anything

timeB3impact: mediumeffort: M

What happens today

With Options::useB3ReduceStrengthFixpoint=false (the default) the pass is single-pass by design, but runSinglePass (b3/B3ReduceStrength.cpp:627–657) still contains a binary escalation: after walk 1 it runs simplifyCFGToFixpoint() and simplifySSA() with m_changed reset, and then:

if (m_didSpecializeSelect || m_changed) {
    m_valueForConstant.clear();
    reduceAllBlocksStrength();   // new RPO, resetValueOwners, Dominators recompute, PureCSE rebuilt, every value re-dispatched
    simplifyCFGToFixpoint();
}
eliminateDeadCodeImpl(m_proc);

A single merged block or a single folded Phi sets m_changed (handleChangedCFGIfNecessary, :4949–4957). Because eliminateDeadCodeImpl runs only before walk 1 (:684) and after walk 2 (:647), walk 2 also re-dispatches every Identity corpse walk 1 left behind — one per non-root constant in FTL input (finding 3).

Why it costs, proposal

For FTL input the trigger is plausibly the common case: FTL::Output::branch never folds constant conditions, so constant branches from lowering are folded in walk 1, which changes the CFG. When triggered, walk 2 roughly doubles the dominant part of the phase (dominators, PureCSE rebuild, per-value dispatch with up to 8 attempts each); with ReduceStrength at roughly 15–25% of B3 time and two runs per compile, the realistic upside is a few percent to ~10% of B3 time. Two options: (a) the cheap one — run eliminateDeadCodeImpl (or a block-local compaction of Identity/Nop values) between the walks so walk 2 does not visit corpses; (b) the targeted one — track dirty blocks (the three blocks produced by specializeSelect, blocks merged or retargeted by simplifyCFG, owner blocks of folded Phis and their users) and run reduceBlockStrength only on those, with PureCSE seeded from dominating blocks. The reviewers flag (b) as hard to make exactly equivalent and as carrying generated-code risk; (a) is safe. Measure with a counter of how often the escalation fires and a CompilerTimingScope around the second reduceAllBlocksStrength.

Air register allocation and liveness

4. Every greedy-allocator LiveRange heap-allocates a 128-byte Deque buffer, and TmpData is 88 bytes

memoryAirimpact: mediumeffort: S–M

What happens today

LiveRange stores its intervals in a Deque<Interval> m_intervals (b3/air/AirAllocateRegistersByGreedy.cpp:373; Interval = WTF::Range<uint32_t>, 8 bytes). Deque with inline capacity 0 starts with m_capacityMask = 0, so the first prepend/append calls expandCapacity(), which allocates max(16, 0) = 16 slots (WTF/wtf/Deque.h:455) — 128 bytes. Every Tmp that is live anywhere pays this, plus every spill and split Tmp created during allocation (addTmpImpl → prepend, :2209–2222), though most SSA-derived Tmps have exactly one or two intervals. sizeof(Deque) is 40 bytes, so LiveRange is 48 and TmpData (:684–738) is 88; m_map is a TmpMap<TmpData> over the absolute index space of both banks (:3636). Coalescables::m_entries (:677) has the same first-growth pattern for any Tmp appearing in a Tmp–Tmp move, and LiveRange::merge/subtract allocate fresh 128-byte buffers as well.

Why it costs, proposal

About 150 bytes and one malloc/free pair per Tmp: ~3 MB and 20k allocator calls for a 20k-Tmp FTL function, ~30 MB and ~10 ms for a 200k-Tmp OMG function, and worse locality in tryAllocate/tryEvict/forEachConflict, which chase the heap pointer for every candidate register. The Deque was chosen for O(1) prepend in the backward liveness walk. Two variants: the zero-logic-change one is Deque<Interval, 4> (Deque sacrifices one inline slot, so 3 intervals inline, TmpData grows to ~120 B but no heap allocation for the common case); the better one is Vector<Interval, 2> with intervals appended in reverse during buildLiveRanges (the backward walk produces them in decreasing order) and one reverse() per Tmp at the end — all prepend producers are confined to buildLiveRanges (:1386, 1555) and addTmpImpl on an empty range. intervals() returns const Deque<Interval>& and is consumed widely, so that variant is a moderate refactor. Also give Coalescables an inline capacity of 2. Measure allocations inside GreedyRegAlloc::buildLiveRanges with a malloc interposer and compare the existing CompilerTimingScopes.

5. A 656-byte PhaseInsertionSet is constructed for every basic block up front

memoryAirimpact: mediumeffort: S

What happens today

PhaseInsertion is Insertion<Inst> (8 + 64 bytes) plus a 4-byte phase, padded to 80 bytes; PhaseInsertionSet holds Vector<PhaseInsertion, 8> (b3/air/AirPhaseInsertionSet.h:91), i.e. a 16-byte header plus 640 bytes of inline storage. GreedyAllocator's constructor builds IndexMap<BasicBlock*, PhaseInsertionSet> m_insertionSets(code.size()) (b3/air/AirAllocateRegistersByGreedy.cpp:850); PhaseInsertionSet is copyable, so the map goes through the fill-with constructor and writes every 656-byte stride. This happens before liveness is even computed, and the vast majority of blocks never receive an insertion (spills and split fixups only). The inline capacity of 8 was inherited from the single-instance, reused Air::InsertionSet pattern, where it is amortized across blocks.

Why it costs, proposal

Roughly 640 bytes per block held for the allocator's whole lifetime, on every optLevel-2 compile (greedy is the only O2 allocator at HEAD): 0.3–1.3 MB for a typical FTL procedure — comparable to the Inst storage of the same blocks — 6.5 MB at 10k blocks and 65 MB at 100k blocks, which can be 10–20% of peak for large OMG functions. Fix is a one-line container change: Vector<PhaseInsertion> m_insertions; (inline capacity 0, 16 bytes when empty, reserveInitialCapacity on first insert), or a sparse map with a Vector<uint32_t> blockToSetIndex and a dense vector appended on first use. No correctness risk. Measure peak RSS around allocateRegistersByGreedy on a large wasm module.

6. PhaseInsertionSet bubble-sorts insertions that arrive as several independently sorted runs

timeAirimpact: medium on spill-heavy wasm, noise on FTLeffort: S

What happens today

PhaseInsertionSet::execute is bubbleSort(m_insertions.mutableSpan()); executeInsertions(...) (b3/air/AirPhaseInsertionSet.cpp:38–39). WTF::bubbleSort is the adaptive cocktail-shaker variant documented as fast for "usually already sorted" input. Within one spill round the per-block appends are indeed sorted (the phase ordering puts SpillMoveTo before SpillMoveFrom). But the allocator appends several runs to the same per-block set before the single execute() at :3366: allocateRegisters<GP>() completes all its rounds before allocateRegisters<FP>(), so the FP run is a second ascending sequence concatenated after the GP run; additional rounds occur whenever newly enqueued spill Tmps evict assigned Tmps that then spill (:2299–2335, :2479–2485); and insertFixupCode appends split-around-clobber and intra-block fixups grouped by Tmp rather than by instruction index (:3337–3442).

Why it costs, proposal

Merging two ascending runs of sizes n₁ and n₂ with bubble sort costs O(n₁·n₂) swaps, each moving three 80-byte records. FTL blocks are small, so this is noise there; a large straight-line wasm block that spills heavily in both banks can have thousands of insertions and spend several to hundreds of milliseconds in execute(). The fix is two lines and preserves identical output: if (!std::ranges::is_sorted(m_insertions)) std::ranges::stable_sort(m_insertions); — operator< orders by (index, phase) and both sorts are stable, so equal keys keep append order. Apply the same guard to Air::InsertionSet::execute and GenericBlockInsertionSet::execute (used by breakCriticalEdges, which also generates non-monotonic indices). Measure with a timing scope around execute() on a spill-heavy wasm module.

7. Air liveness materializes a 64-byte use/def record per instruction boundary that the dense solver reads once

bothAirimpact: mediumeffort: M

What happens today

LivenessAdapter::prepareToCompute allocates, per block, a Vector<Actions> of size()+1 entries where Actions is two Vector<unsigned, 4> (b3/air/AirLivenessAdapter.h:54–61, 76–101). sizeof(Vector<unsigned, 4>) is 32 bytes (pointer, capacity, size, 16 bytes inline), so each boundary costs 64 bytes — exactly sizeof(Inst) — and boundaries with more than four distinct uses or defs (calls, and every OSR-exit Patch carrying dozens of ColdUse args) spill to the heap and pay appendIfNotContains's linear scan. In the dense solver, which is the default below a 32M-bit budget, computeDense reads the actions exactly once to derive gen/kill (WTF/wtf/Liveness.h:469–488); the fixpoint never touches them again, yet the table stays alive until the Liveness object dies. The greedy allocator builds a UnifiedTmpLiveness (AirAllocateRegistersByGreedy.cpp:1299), uses only liveAtHead/liveAtTail, and then re-derives the per-instruction early/late use/def lists with its own forEachTmp walk (:1476–1496). At optLevel 2 the structure is built twice (greedy, then StackSlotLiveness in the stack allocator), plus RegLiveness passes.

Why it costs, proposal

Memory: ~64 bytes per boundary per instance — 6.4 MB per 100k instructions, overlapping the greedy allocator's TmpData map and liveness matrices. Time: one extra role-aware instruction walk with vector appends, duplicated by greedy's second pass; the reviewers put this at 3–6% of buildLiveRanges. Two options: (a) a CSR layout — per block one flat use-index vector, one def-index vector and a boundary-offset array, deduplicated with a per-block generation set — drops the cost to 8 bytes per boundary plus 4 per actual entry and removes the per-boundary heap spills and the quadratic dedup; (b) a "no actions cache" mode for dense-only clients that need only head/tail sets, where prepareToCompute sets gen/kill bits directly from inst.forEach<Thing> — the greedy allocator would opt in and could also feed its second pass from the same walk. Option (b) must keep actions for computeSparse and for LocalCalc clients (stack allocator, RegLiveness::LocalCalcForUnifiedTmpLiveness). Results are bit-identical. The existing CompilerTimingScope("Air", "Liveness") measures it.

12. Every Air basic block allocates at least 1 KB of Inst storage

memoryAirimpact: mediumeffort: S

What happens today

BasicBlock::InstList is a plain Vector<Inst> (b3/air/AirBasicBlock.h:55) and WTF::Vector's default minCapacity is 16 (WTF/wtf/Forward.h:166), so the first append to any block allocates 16 × 64 = 1024 bytes. Air CFGs contain many one-to-three-instruction blocks: critical-edge pads (AirBreakCriticalEdges.cpp:47–49), loop entry/exit pads, FTL check and slow-path blocks, wasm br_if continuations. Larger blocks carry up to 33% slack from 1.5× growth because B3LowerToAir::finishAppendingInstructions (b3/B3LowerToAir.cpp:1761–1769) appends one at a time even though it knows the total beforehand. No reserveInitialCapacity or shrinkToFit exists anywhere in b3/air for Inst vectors.

Why it costs, proposal

For a 3k-block / 30k-Inst function, roughly 1.9 MB of live Insts versus ~1.4 MB of minimum-capacity slack plus growth slack — wasted Inst storage comparable to used storage, held for the entire Air pipeline. Declare InstList as Vector<Inst, 0, CrashOnOverflow, 2> (or 4), call reserveInitialCapacity with the exact total in finishAppendingInstructions and in lowerEntrySwitch's clone loop. 13. CheckSpecial builds a throwaway Inst on every query, and every Patch walk pays virtual per-arg dispatch

timeAir / B3 Specialsimpact: low–mediumeffort: M

What happens today

Simple Air opcodes answer forEachArg, admitsStack and isValidForm from the generated g_formTable. Patch instructions instead go PatchCustom::forEachArg → virtual Special::forEachArg → StackmapSpecial::forEachArgImpl, which per argument does a bounds-checked m_reps read, a child.value()->type() load from an otherwise-cold B3 Value, a switch on the rep kind, and an indirect ScopedLambda call (b3/B3StackmapSpecial.cpp:75–152). CheckSpecial goes further: forEachArg, isValid, admitsStack, shouldTryAliasingDef and generate each call hiddenBranch(), which copies the check args into a Vector<Arg, 8> and constructs a temporary Inst (b3/B3CheckSpecial.cpp:102–110); since Inst keeps only three args inline, the Vector&& constructor calls releaseBuffer(), which mallocs a 64–80-byte buffer that the temporary's destructor frees (b3/air/AirInst.h:79–89). This applies to CheckAdd on both architectures (4 args), arm64 CheckSub/CheckMul (4–5 args) and x86_64 immediate CheckMul; plain Check (3 args) stays inline.

Why it costs, proposal

Air walks each instruction's args on the order of 10–15 times per compile (padInterference, analyzeCode, greedy's passes plus admitsStack per Tmp arg, liveness ×2, spill insertion, RegLiveness ×2, stack allocation, lowerStackArgs, generate). In FTL output Patch args — every check carries the live state — can be a large share of all Air args, at ten times the per-arg cost of the table path; reviewers estimate several percent of Air time, with the hiddenBranch malloc a smaller additive term (~15–30 malloc/free pairs per checked arithmetic op). Proposal: have B3LowerToAir::fillStackmap, which already visits every constrained child, record one ENCODE_INST_FORM byte per stackmap arg so that forEachArgImpl becomes a flat loop over bytes (keeping only the ForceLateUseUnlessRecoverable identity test dynamic); and have opcode_generator.rb emit forEachArgSimple(Opcode, std::span<Arg>, …) and admitsStack(Opcode, std::span<const Arg>, unsigned) overloads so CheckSpecial can query the form table for its arg sub-span without materializing an Inst, reserving the Inst-building path for generate(). Caching per-stackmap forms also removes the last reason Air needs stackmap children's Values alive, enabling more freeing in finding 2. Validate against the dynamic computation under the Air validation options; count hiddenBranch() calls per compile.

17. lowerAfterRegAlloc recomputes whole-function register liveness for a handful of ColdCCall/Shuffle instructions

bothAirimpact: low–mediumeffort: M

What happens today

After the allocator, lowerAfterRegAlloc needs the set of physical registers live after each ColdCCall/Shuffle. It gets it by running padInterference over every adjacent instruction pair, constructing a RegLiveness (a forEach<Reg> walk over every instruction building two RegisterSets per boundary, gen/kill sets and a CFG fixpoint, b3/air/AirRegLiveness.cpp:42–130) and running a backward LocalCalc over every instruction of every block (b3/air/AirLowerAfterRegAlloc.cpp:62–90), although only the blocks containing a relevant instruction ever read the result. Because usesColdCCall is set for any rare CCall at O2 — FTL's vmCall slow paths, OMG's slow-path operations — essentially every optimized compile pays this, and reportUsedRegisters runs another RegLiveness right after.

Proposal

In GreedyAllocator::assignRegisters(), which already visits every instruction with all assignments final, compute for each ColdCCall/Shuffle the set of registers whose assigned intervals cover the instruction's late point (m_regRanges[reg].m_allocations) plus pinned registers, and stash it in a side table on Code that lowerAfterRegAlloc consumes, dropping its padInterference, RegLiveness and the all-blocks LocalCalc. The reviewers note two complications: fixup insertion after point assignment means interval points no longer map 1:1 to instruction positions, and pinned-register modelling must match RegLiveness exactly; a simpler intermediate step is to run the LocalCalc only over blocks that contain a relevant instruction (one cheap opcode scan first). Roughly three full instruction walks and 32 bytes per boundary transient on every FTL compile — plausibly 2–4% of Air time.

18. Spill-code emission walks the entire function per bank per round

timeAirimpact: low–mediumeffort: M

What happens today

spill() only flips m_needsEmitSpillCode (b3/air/AirAllocateRegistersByGreedy.cpp:3015–3042); emitSpillCodeAndEnqueueNewTmps (:3076–3335) then scans every Tmp of the bank for Stage::Spilled to allocate slots, and visits every instruction in the function running forEachArg (in-place spill and rematerialization attempts with admitsStack/isValidForm/spillSlot() lookups) followed by forEachTmp (load/store insertion). The batching comment at :3038–3039 explains that this avoids one traversal per spilled Tmp, but each round still costs two full role-aware walks regardless of how few Tmps spilled, and additional rounds happen whenever newly enqueued Unspillable spill Tmps evict assigned Tmps that subsequently spill (:2299–2335).

Proposal

Maintain a BitVector of dirty blocks: in spill(), call forEachBlockInLiveRange (:1047–1067) and mark each block — the live range covers every point at which the Tmp is used or defined, including after split-around-clobbers, since holes are only punched at instructions that do not reference it. Iterate only dirty blocks in emitSpillCodeAndEnqueueNewTmps, and keep a Vector<Tmp> m_newlySpilled to replace the O(numTmps) slot scan. Reviewers cap the expected win: the spill heuristic prefers long-range Tmps, whose ranges cover much of the function, so the dirty set is often large; for lightly spilling functions the win is most of the phase. Wrap the function in a CompilerTimingScope and count rounds per bank to measure.

Why it costs, proposal

For ordinary CFGs (in-degree ≤ 8) this is linear in practice. 16. WTF::Dominators allocates a 128-byte Vector per non-leaf tree node, and B3 rebuilds it 8–12 times

bothWTF / B3 (also DFG)impact: loweffort: S

What happens today

The dominator computation itself is already Semi-NCA with compact 16-bit state, but the result keeps one Vector<Node> idomKids per block (WTF/wtf/Dominators.h:919), appended to as each block's idom is discovered (:66–68). With minCapacity = 16, the first append on every non-leaf dominator-tree node mallocs 128 bytes of which 8–16 are typically used, so a build costs ~0.4–0.6·N malloc/free pairs and ~100 KB per 1000 blocks. Procedure memoizes Dominators, NaturalLoops and the backwards variants until invalidateCFG() (b3/B3Procedure.cpp:337–363), but the pipeline invalidates often (ReduceStrength ×1–3 per run, hoistLoopInvariantValues, CSE after breakCriticalEdges, fixSSA, foldPathConstants, moveConstants), so a typical optLevel-2 compile builds it 8–12 times plus 3–4 NaturalLoops and a BackwardsDominators.

Proposal

Simplest: intrusive first-child/next-sibling links — replace Vector<Node> idomKids with Node firstKid; Node nextSibling; in BlockData (same 32 bytes, zero allocations, built in the same loop by prepending). Alternatively a CSR layout (one flat kids vector plus per-block offsets built by count/prefix-sum/fill). The only readers are the pre/post numbering DFS (:102), forAllBlocksDominatedBy/StrictlyDominatedBy (:177–193) and dump. DFG shares the template and benefits too. Absolute cost is modest (sub-ms to low-ms per compile) but it is pure overhead; Dominators has a selfCheck mode to validate identical answers.

19. LowerToAir housekeeping: dead analyses, 272 bytes per value, and missing VectorTraits

bothB3→Airimpact: loweffort: S

Three small, independent items in b3/B3LowerToAir.cpp that together trim a few percent of the phase.

Dead preferRightForResult(). The function (:989–1025) is only reachable from appendBinOp (:1143–1150) and the CheckAdd path (:6313) after an isValidForm(opcode, Tmp, Tmp, Tmp) test fails — and every commutative opcode pair plus BranchAdd32/64 has an unprefixed three-operand form in AirOpcode.opcodes on both x86_64 and arm64. To support it, the lowering constructs PhiChildren (16 bytes per value index, zero-filled, plus a heap vector per Phi) and a full UseCounts whose constructor sorts every value's children to compute numUsingInstructions (O(k log k) per stackmap value with dozens of children). Delete the function and its two call sites, switch m_useCounts to UseCountsWithoutUsingInstructions (every remaining user calls numUses() only), and drop m_phiChildren.

Vector<Vector<Inst, 4>> m_insts (:6800). Each inner element is 272 bytes and the outer vector is retained at the largest block's value count; every Inst is moved once on outer growth and once more into an unreserved Air block. Replace with a flat Vector<Inst> plus a Vector<unsigned> of group starts, and reserveInitialCapacity the Air block in finishAppendingInstructions (finding 12).

No VectorTraits for Air::Inst, Arg, Tmp. Inst has a user-defined move and destructor, Arg and Tmp user-provided default constructors, so canMoveWithMemcpy is false and every Vector growth, removeAllMatching compaction (DCE, stack allocator, assignRegisters) and removeAt moves elements one at a time with a branch and a variable-length memcpy. All three are trivially relocatable (the out-of-line arg pointer is uniquely owned). A three-line template<> struct VectorTraits<JSC::B3::Air::Inst> : VectorTraitsBase<false, void> { static constexpr bool canMoveWithMemcpy = true; }; (and the same for Arg/Tmp, or making Arg's constructor = default) turns those into bulk memcpys; one reviewer notes executeInsertions has its own shifting loop and would not benefit. Roughly 1% of Air time, risk-free.

Suggested order of attack and how to measure

Start with the changes that are small and carry no codegen risk, because they can land independently and each has a clear before/after: the fixSSA emptiness check (10), PhaseInsertionSet inline capacity and sort guard (5, 6), Air InstList minimum capacity and reservation (12), the VectorTraits specializations and dead preferRightForResult (19), the Dominators tree layout (16), the predecessor rewrite (15) and the CSE sole-holder filter (9). Then the two FTL front-end changes (3), which shrink the input to every downstream phase, and the two-stage exit-capture cleanup (1, stages 1–2). The larger items — OMG origin retention (2), the LiveRange container (4), liveness actions (7), the CSE re-sweep (8), ReduceStrength's second walk (14), Patch form caching (13), allocator-derived register liveness (17) and dirty-block spill emission (18) — each deserve a measurement first.

The existing instrumentation is sufficient for most of this. JSC_logPhaseTimes=1 and JSC_reportTotalPhaseTimes=1 report every CompilerTimingScope, and every B3 and Air PhaseScope is one; the greedy allocator already has scopes for buildLiveRanges and allocateRegisters, and Air liveness has its own. JSC_dumpB3GraphAtEachPhase=1 and JSC_dumpAirGraphAtEachPhase=1 give value and instruction counts per phase. Two gaps are worth closing first: add a CompilerTimingScope around FTL::lowerDFGToB3, because today it is attributed to DFG time (dfg/DFGPlan.cpp:474–477); and add a per-compile allocation counter (a malloc interposer, or fastMallocStatistics deltas around prepareForGeneration) so the memory findings can be quantified rather than estimated. Run everything with JSC_useConcurrentJIT=0 so the compile thread is the measured thread, on an FTL-heavy JavaScript workload and on a large wasm module for the OMG-specific items (2, 10, 15).

For the avoidance of repeated proposals: B3::Value is 40 bytes with trailing inline children and no per-opcode payload bloat (b3/B3Value.h:933–941); Air::Inst is exactly 64 bytes with three inline args and a custom out-of-line buffer (b3/air/AirInst.h:321); Air::Arg is 16 bytes with unions (AirArg.h:1850–1867); ReduceStrength is single-pass by default (useB3ReduceStrengthFixpoint=false); canonicalizePrePostIncrements is off by default; LowerToAir already uses IndexSet/IndexMap for m_locked/m_valueToTmp (B3LowerToAir.cpp:6787–6789); CheckSpecial instances are hash-consed per shape; WTF::Liveness uses dense bitset gen/kill with a 4 MB budget and a sparse fallback; the greedy allocator fuses TmpWidth and UseCounts into one walk; Procedure memoizes dominators and loops; freeUnneededB3ValuesAfterLowering already sheds the B3 graph for FTL; simplifyCFG reserves capacity when merging blocks; IR validation and dumping are fully gated behind options in release builds.

Appendix C — Method

Ten slice analysts, twenty adversarial verifiers (one factual, one impact/feasibility per slice), one completeness critic with two further verifiers: 33 agents, ~1,900 file reads and searches, all against the checkout at c73014505a. Findings that a verifier could not confirm from the code were to be dropped; none were. Findings that were found independently by more than one analyst (the OMG origin retention, the PhaseInsertionSet buffer and sort, the exit-state capture, predecessor recomputation, the liveness actions table, the Deque growth) were merged. Impact ratings are the verifiers' consensus and, where the two disagreed, the report gives the range. No claim in this document rests on a measurement.
