JavaScriptCore Realm Audit

A deep dive through the parser, bytecode, LLInt, Baseline, DFG/FTL, runtime, object model and heap looking for one class of bug — code that acts on behalf of the wrong JSGlobalObject. Eighteen findings, each with a runnable jsc reproducer: five ShadowRealm boundary escapes, four behaviours that change when a function tiers up into DFG/FTL, and nine wrong-realm results or leaks in the runtime, object model and heap. Fourteen of them also reproduce in Bun 1.3.14 through node:vm — where ShadowRealm is on by default.

Headline results

  • Function.prototype.caller hands out functions from other realms and walks straight through ShadowRealm wrappers — a complete callable-boundary escape in both directions (F1).

Findings at a glance

A realm is a JSGlobalObject: one set of intrinsics (Array.prototype, %Promise%, TypeError…), one global scope, one bag of per-realm state (watchpoints, legacy RegExp statics, the Math.random generator, template maps). Realms that share a VM — same-origin iframes, ShadowRealms, createGlobalObject() in the shell — freely exchange objects, so every engine operation has to decide whose intrinsics and state it uses. ECMA-262 answers with the “current realm” (the realm of the running function object) plus explicit GetFunctionRealm/species lookups. The bugs below are places where JSC answers differently, answers inconsistently between execution tiers, or lets an object cross a boundary it must not cross.

Severity is judged for an engine embedded in a browser: high breaks an isolation guarantee, medium is an observable spec deviation reachable from ordinary cross-frame code or one that changes with JIT tier, low needs contrived code or only moves an error object's realm. tier marks behaviour that differs between LLInt/Baseline and DFG/FTL for the same program.

Where realm identity enters JSC

The useful mental model: nothing before CodeBlock linking knows what a realm is, everything after it must never forget. The figure marks the stages, what each one knows, and where the findings sit.

Lexer, parser, bytecode: nothing to get wrong

Source/JavaScriptCore/parser/ and bytecompiler/ do not reference JSGlobalObject except to build a SyntaxError for a given realm (parser/ParserError.h:92-115) and to create module records. CodeCache (runtime/CodeCache.cpp) is keyed by SourceCodeKey — source, strictness, script mode, derived-context and eval-context type, arrow-function context, code-generation mode flags — none of which is realm state, so an UnlinkedCodeBlock is legitimately shared by every realm in the VM. Realm-dependent operations are expressed indirectly: link-time constants (@Array, @Object, @promiseResolve…), op_resolve_scope/op_get_from_scope against the CodeBlock's global object, allocation profiles and inline-cache metadata that live in the linked CodeBlock. I looked specifically for per-realm inputs to code generation that bypass the cache key (per-global feature toggles read by the parser, cached template objects or RegExp objects on unlinked executables, allocation structures on UnlinkedFunctionExecutable) and found none; the direct-eval cache is per CodeBlock, and eval() correctly treats another realm's eval function as an indirect eval (interpreter/Interpreter.cpp:110 compares against the caller realm's evalFunction()).

LLInt and Baseline: realm is data, not code

The LLInt reads the global object out of the CodeBlock register; Baseline code has been “unlinked” since 2021 — compiled once per UnlinkedCodeBlock and shared across realms — so it cannot bake a realm pointer in even by accident: loadGlobalObject() goes through the constant pool, thunks such as the Math.random fast path load the realm from the callee (jit/AssemblyHelpers.cpp:900-905), and inline-cache stubs that need a global object (custom accessors, getter/setter calls) take it from the owning StructureStubInfo. The one realm decision these tiers make by hand is on the call path — which realm's TypeError to throw when a callee is not callable/constructible — and that is where F11(a) lives.

DFG and FTL: globalObjectFor(codeOrigin) and the intrinsic gap

Optimized code is per CodeBlock, so realm pointers are constants, and inlining routinely mixes realms in one graph. The graph handles that with m_graph.globalObjectFor(node->origin.semantic), which returns the realm of the inlined function a node came from — correct for inlined JS, including builtins written in JS. The gap is intrinsic inlining: when the bytecode parser replaces a call to a C++ built-in with a DFG node there is no inlinee frame, so globalObjectFor() yields the caller's realm although LLInt/Baseline would have run the built-in in its own. JSC knows this: calleeMayBeCrossRealm() (dfg/DFGByteCodeParser.cpp:2604-2610) refuses to inline a foreign (or unknown) callee and guards a dozen intrinsics, and the RegExp intrinsics thread an explicit GetGlobalObject(callee) child. F2–F5 are the intrinsics that were missed. A useful amplifier to keep in mind: NativeExecutables are VM-wide, so a call site that has seen the same built-in from two realms becomes a closure call whose CallVariant has no function but still reports the intrinsic — calleeMayBeCrossRealm() conservatively bails in that case, the unguarded intrinsics compile caller-realm behaviour for everybody.

Runtime: “fast and non-observable” has a realm in it

Host functions receive the callee's realm, which is exactly the spec's current realm, so straightforward C++ built-ins are right by construction (I spot-checked the realm of the thrown error for two dozen built-ins called cross-realm with bad arguments; all but the F11 cases were correct). The recurring bug shape is a fast path that (1) proves via watchpoints/structures that skipping an observable protocol step is safe — correctly consulting the receiver's realm, e.g. RegExpObject::isSymbolMatchFastAndNonObservable() uses this->realm() — and then (2) runs the shortcut with the globalObject in hand, i.e. the callee's realm, although the skipped step would have transferred control into the receiver's realm. Results then materialise in the wrong realm, and flip to the right one as soon as an unrelated watchpoint in the receiver's realm fires (F6–F8).

Object model and heap

Every Structure records its realm; JSObject::realm() is that, a JSFunction's realm is its scope chain's global object, and getFunctionRealm() implements the spec operation including bound-function and proxy unwrapping (a revoked proxy correctly throws). Prototype-keyed structure caches are per realm; InternalFunction::createSubclassStructure re-validates cached new.target structures against both ClassInfo and realm; ObjectAllocationProfile falls back to GetFunctionRealm(newTarget)'s %Object.prototype% (verified with cross-realm Reflect.construct for plain functions, classes, Array, Promise and bound new.target). The heap is one per VM and realm-agnostic; the realm-relevant pieces are the routing of microtasks and deferred work to a global object (see the note under F7/F16) and the cross-realm heap walk in JSGlobalObject::haveABadTime(), which held up under the indexed-accessor-on-foreign-prototype tests I threw at it. The one deliberate realm-relative rule in the object model is masquerades-as-undefined (F12).

F2foreignPromise.then() allocates the derived promise in the caller's realm after tier-up

mediumtier-dependentconfirmed in jsc

Calling .then on a promise that came from another realm is the normal case whenever promises cross an iframe boundary. In LLInt/Baseline the callee is realm B's Promise.prototype.then, so promiseProtoFuncThen runs with B's global object and the derived promise is a B promise — which is also what the spec produces via SpeciesConstructor. Once the calling function is hot, the DFG bytecode parser turns the call into a PromiseThen node without asking calleeMayBeCrossRealm(); PromiseObjectUse is only a cell-type check, so the foreign promise sails through, and the backend calls operationPromiseThen with the node origin's (realm A's) global object, which lands in JSPromise::then → JSPromise::create(vm, globalObject->promiseStructure()).

F3DFG String.prototype.{match, search, split} and RegExp.prototype[@@split] intrinsics run in the caller's realm — a monkey-patch in the callee's realm is silently dropped

mediumtier-dependentconfirmed in jsc

These recently C++-ified String methods have DFG intrinsics whose only precondition is the caller's stringSymbol{Match,Search,Split}WatchpointSet (m_graph.isWatchingStringSymbolSplitWatchpoint(currentCodeOrigin()) etc.). When the callee is realm C's String.prototype.match — say a parent frame installed a child frame's String methods, or a library holds uncurried references — LLInt/Baseline execute C's built-in, which does RegExpCreate in C and honours C's RegExp.prototype[@@match]. The DFG node lowers to operationStringMatch/Search/Split(lexicalGlobalObject, …), so it consults and allocates in realm A: an override of RegExp.prototype[Symbol.match] or [Symbol.search] in realm C stops being called once the caller is optimized, result arrays change realm, and the legacy RegExp.lastMatch/$1 statics are written into the wrong realm. In Fixup, StringMatch/StringSearch with a RegExp argument are likewise converted to RegExpMatchFast/RegExpSearch with a hard-wired JSConstant(globalObjectFor(origin)).

F6String.prototype methods with a foreign RegExp: the fast path runs the match in the caller's realm

mediumall tiersconfirmed in jsc

"text".match(re) where re came from another frame is ordinary code. stringProtoFuncMatch asks regExpObject->isSymbolMatchFastAndNonObservable() — which, correctly, inspects the RegExp's own realm B (its regExpPrimordialPropertiesWatchpointSet, its RegExp.prototype) — and on success calls regExpMatchFast(globalObject, …) with the globalObject of String.prototype.match, i.e. realm A. Everything the skipped @@match call would have done in realm B now happens in realm A: the matches array comes from A's regExpMatchesArrayStructure, matchAll's species-cloned RegExp and its %RegExpStringIterator% are A objects, split's array is an A array, and the legacy statics (RegExp.lastMatch, RegExp.$1…) are recorded on A's RegExpGlobalData while B's stay stale. The behaviour is not self-consistent: fire an unrelated watchpoint in B — the reproducer deletes and re-adds the very same RegExp.prototype.exec — and the identical call now takes the generic path, invokes B's @@match, and everything lands in realm B.

F7Promise.prototype.then/catch/finally ignore SpeciesConstructor for foreign promises

mediumall tiersconfirmed in jsc

JSPromise::then takes its fast path when promiseSpeciesWatchpointIsValid(vm, this) — evaluated against the promise's realm — and then allocates JSPromise::create(vm, globalObject->promiseStructure()) in the realm of the then being executed. promiseSpeciesConstructor() encodes the same assumption: for any JSPromise with a valid watchpoint it returns globalObject->promiseConstructor() rather than promise->realm()->promiseConstructor(). So Promise.prototype.then.call(foreignPromise, f) — the defensive idiom used by promise utilities, zone/async-context shims and SES-style code precisely because it does not trust foreignPromise.then — yields a promise of the caller's realm; catch and finally inherit it. Twenty lines further down, JSPromise::promiseResolve gets the same question right (constructor == promise->realm()->promiseConstructor()), and Promise.all/race/any/allSettled wrap foreign promises correctly, so this is an oversight rather than a policy. As with F6 the answer flips to the correct realm once B's species watchpoint is invalidated. F2 is the DFG-flavoured way to reach the same line of code from an ordinary bP.then().

Heap and GC

The collector itself is realm-agnostic — one Heap per VM, subspaces by cell type, no per-realm marking state — so “realm bugs in the GC” reduce to two questions: does any per-realm cache keep another realm alive or hand its objects out under the wrong realm, and does the cross-realm heap walk in JSGlobalObject::haveABadTime() (which must find every array whose prototype chain reaches a newly “bad” realm's Array.prototype/Object.prototype) miss anything. Bun's node:vm: which findings carry over

Bun is built on JavaScriptCore, and its node:vm implementation creates each context as another JSGlobalObject (NodeVMGlobalObject) inside the same JSC::VM as the main program — exactly the “several realms, one VM” situation the findings depend on. Two things stand out. First, everything that is pure C++ runtime or object model (F7–F11, F17) transfers one-to-one: a vm context in Bun is a realm in the full sense, so “sandbox” code that hands promises, buffers, generators or constructors across the context boundary sees exactly the WebKit behaviour, including the watchpoint-dependent flips. Second, the JIT findings transfer according to age: Bun's snapshot has the PromiseThen intrinsic (F2) and the older unguarded intrinsics (F4, F5) but not this summer's String intrinsics (F3), and it lacks the guard that upstream has since added to Object.keys — a reminder that the calleeMayBeCrossRealm sweep is worth back-porting as a unit rather than piecemeal.

The ShadowRealm rows are the ones that matter operationally. In WebKit they are pre-ship bugs behind a flag; in Bun 1.3.14 new ShadowRealm() works out of the box, so F1, F13, F14 and F15 are four independent, flagless ways for code inside a ShadowRealm to obtain the host realm's Function constructor (and for host code to be handed raw shadow-realm objects). Anyone using ShadowRealm in Bun as an isolation boundary today does not have one. node:vm itself never promised isolation (Node's documentation says as much), so F1 between plain contexts is “only” a spec deviation there — V8 does the same — but it is worth knowing that a sloppy-mode function inside a Bun vm context can reach its caller's function object in the main realm.

Checked and found correct

Negative results are most of the value of an audit like this, so here is what held up — each item was either read to the bottom or exercised cross-realm in the shell (usually both), cold and after tier-up.

Front end and linking

  • Parser/BytecodeGenerator take no JSGlobalObject; SourceCodeKey covers every codegen input; nothing realm-specific is cached on Unlinked* objects; symbol tables are cloned per realm; template objects are cached on the per-realm ScriptExecutable; RegExp literals allocate with the run-time realm's structure.
  • Direct eval compares the callee against the caller realm's eval (interpreter/Interpreter.cpp:110), so another realm's eval is correctly an indirect eval in that realm; the direct-eval cache is per CodeBlock.

LLInt, Baseline, ICs, thunks

  • No compile-time realm in Baseline code: loadGlobalObject(), LazyBaselineGlobalObject for truthiness/masquerade checks, scope-resolution thunks reading epoch/var-injection state from the loaded realm, instanceof comparing against the run-time realm's Function.prototype[@@hasInstance].
  • Handler ICs load the realm from PropertyInlineCache per CodeBlock; shared stubs are keyed by AccessCase::canBeShared tightly enough that the remaining immediates are identical for all sharers. Custom accessors and custom values consistently receive the holder's realm in LLInt (runtime/PropertySlot.cpp), Baseline ICs and DFG — the DFG refuses to inline a custom accessor whose holder is from another realm (bytecode/GetByStatus.cpp:358-360, PutByStatus.cpp:267-268), which I confirmed with B.RegExp.lastMatch read from a hot A function (the getter would throw if it were handed the wrong realm; it never did).
  • Native-call trampolines pass callee->scope()'s realm for host JSFunctions and InternalFunction::globalObject() otherwise; “not a function/constructor” errors are created in the caller's realm in both LLInt and the call ICs (F11 is the one asymmetry).
  • iterator_open/iterator_next fast paths require the fetched @@iterator to be identical to the lexical realm's Array.prototype.values etc., so foreign iterables go generic: a monkey-patched Array.prototype[Symbol.iterator] or %ArrayIteratorPrototype%.next in the iterable's realm is honoured by for-of, spread, destructuring, Array.from, new Set/Map, Math.max(...x) — cold, hot, patched before or after tier-up, monomorphic or mixed-realm call sites.

DFG/FTL

  • Guarded intrinsics: Array/TypedArray entries/keys/values, slice, splice, concat, Object.keys/getOwnPropertyNames/getOwnPropertySymbols, Map/Set iterator creation and next, string iterator, %RegExpStringIterator%.next; RegExp.prototype.exec/test/@@match/@@search carry GetGlobalObject(callee) and pin the receiver to the lexical regExpStructure; Array/TypedArray constructors and handleConstantFunction's Object/String/RegExp/Map/Set/ArrayBuffer/Symbol use function->realm(); Array.of checks this against the lexical constructor; indexOf/includes/join/sort pin original array structures of the lexical realm so foreign arrays OSR-exit.
  • Every m_codeBlock->globalObject() in the bytecode parser is m_inlineStackTop's (the inlinee's) code block; OSR-exit/materialisation code derives realms per inline frame; StrengthReduction refuses to fold a cross-realm NewRegExpUntyped. A battery of roughly seventy other built-ins (iterators, Object.keys/values/entries, Array.of/from, slice/concat/map/filter/splice/flat, JSON.parse, RegExp exec/split/matchAll, typed arrays, boxed primitives, constructors) was driven cross-realm cold vs hot by the runtime sub-audit with no flips beyond F2–F5.

Runtime and object model

  • ArraySpeciesCreate implements the cross-realm %Array% carve-out; typed-array species checks inSameRealm; typedArray.buffer materialises in the view's realm; Array.prototype.concat honours a foreign realm's @@isConcatSpreadable; JSON's fast stringifier checks prototype identity so a foreign Object.prototype.toJSON is honoured; Object.assign/spread clone fast paths require same realm and prototype.
  • Promises other than F2/F7: Promise.resolve wraps foreign promises (constructor identity via promise->realm()), all/race/any/allSettled route foreign promises through the thenable job (patched foreign then is called the right number of times), await of a foreign promise takes the spec's two extra ticks and honours a patched then, async-generator results use the generator's realm.
  • GetPrototypeFromConstructor fallbacks: Reflect.construct with a cross-realm new.target whose .prototype is not an object yields new.target's realm's intrinsic for plain functions, classes, Array, Promise, generator functions, and a bound new.target unwraps to its target's realm; allocation-profile caches are keyed so that no cross-realm poisoning occurs; Reflect.construct(B.Object, [v], ntA) follows the spec's “NewTarget is not the active function” branch.
  • Reified custom-accessor functions (Object.getOwnPropertyDescriptor(B.RegExp, "lastMatch").get) are created in the holder's realm and are identical whichever realm asks; the legacy RegExp static accessors read and write the receiver's realm; Intl's legacy-constructor symbol is per realm; Iterator.from wraps foreign iterators; two dozen built-ins called cross-realm with bad arguments (B.Array(-1), B.JSON.parse("{"), B.BigInt(1.5), new B.Uint8Array(-1), calling a B class without new, …) threw the callee realm's error as the spec requires — F11 lists the exceptions.
  • Cross-realm “having a bad time”: with an indexed accessor on realm A's Array.prototype, objects and arrays created in other realms (including realms created afterwards) whose chain reaches it were SlowPutArrayStorage and hit the setter, in the interpreter and from a hot DFG store — see the heap note above.

Method and reproduction

The audit combined three things. First, a read of every place a JSGlobalObject* is chosen rather than merely passed along — DFG's intrinsic and accessor inlining, the C++ fast paths that skip an observable protocol step, ShadowRealm marshalling, legacy reflection, lazily materialised wrappers — done partly by me and partly by five parallel sub-audits (DFG/FTL, runtime fast paths, ShadowRealm, LLInt/Baseline/IC sharing, object model/GC) whose candidate lists I then tried to break. Second, differential testing in a JSCOnly release build of this checkout: the same operation performed on same-realm and foreign-realm objects (createGlobalObject()), and the same call executed cold and after 105 iterations with --useConcurrentJIT=0, comparing which realm's prototypes, errors and per-realm state were involved. Third, checking each surviving candidate against the current spec text; several plausible candidates died here or in the shell (custom-accessor inlining, allocation-profile poisoning, iterator fast paths, JSON, species for arrays and typed arrays), and they are recorded in the previous section rather than silently dropped.
