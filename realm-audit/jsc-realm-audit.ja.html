JavaScriptCore Realm 監査

パーサ、バイトコード、LLInt、Baseline、DFG/FTL、ランタイム、オブジェクトモデル、ヒープを縦断し、ただ一種類のバグ——誤った JSGlobalObject の名義でコードが動く箇所——を探した記録です。所見は18件、すべてに実行可能な jsc 再現スクリプトが付きます。内訳は ShadowRealm 境界からの脱出が5件、関数が DFG/FTL にティアアップすると挙動が変わるものが4件、ランタイム・オブジェクトモデル・ヒープでの誤 realm の結果やリークが9件。うち14件は Bun 1.3.14 の node:vm でも再現し、しかも Bun では ShadowRealm がデフォルトで有効です。

  • チェックアウト WebKit main, 363100839e
  • バイナリ JSCOnly リリースビルド、x86_64 Linux
  • 手法 ソース読解 ＋ realm 間・JIT ティア間の差分テスト
  • 追加検証 Bun 1.3.14（node:vm）、V8 参照として Node 22

要点

  • Function.prototype.caller が他 realm の関数を返し、しかも ShadowRealm のラッパフレームを素通りする——双方向に成立する完全な callable boundary 脱出です（F1）。
  • iframePromise.then() は、呼び出し元の関数が DFG に到達した途端に別 realm の Promise を返すようになります——PromiseThen intrinsic がクロス realm ガードの一斉適用から漏れていました（F2）。同じ穴を持つ DFG intrinsic がほかに5つあります（F3–F5）。
  • String×RegExp、Promise.prototype.then、ArrayBuffer.prototype.slice のランタイム高速パスは、レシーバの realm を検証しておきながら呼び出し側の realm で実行するため、無関係なウォッチポイントが発火すると結果の realm が反転します（F6–F8）。
  • Bun 1.3.14 は18件中14件を node:vm コンテキスト経由で引き継いでおり、Bun は ShadowRealm をフラグなしで公開しているため、F1/F13/F14/F15 は現時点で実際に動作するサンドボックス脱出です（Bun の節）。
  • フロントエンドは構造上 realm と無縁です。CodeBlock のリンク以前に realm バグは起こり得ず、LLInt/Baseline のコード共有や IC スタブ共有にも問題は見つかりませんでした。

所見一覧

realm（レルム）とは JSGlobalObject のことです。intrinsic 一式（Array.prototype、%Promise%、TypeError…）、グローバルスコープ、そして realm ごとの状態（ウォッチポイント、レガシーな RegExp 静的プロパティ、Math.random の生成器、テンプレートマップ）を1組ずつ持ちます。同じ VM を共有する realm——同一オリジンの iframe、ShadowRealm、シェルの createGlobalObject()——は自由にオブジェクトをやり取りするため、エンジンのあらゆる操作は「誰の intrinsic と状態を使うのか」を決めなければなりません。ECMA-262 の答えは「current realm」（実行中の関数オブジェクトの realm）と、明示的な GetFunctionRealm／species の参照です。以下のバグは、JSC がそれと違う答えを出す箇所、実行ティアによって答えが食い違う箇所、あるいは越えてはならない境界をオブジェクトに越えさせてしまう箇所です。

深刻度はブラウザに組み込まれたエンジンとして評価しています。高 は隔離の保証を破るもの、中 は通常のクロスフレームコードから到達できる観測可能な仕様逸脱、または JIT ティアで挙動が変わるもの、低 は不自然なコードが必要か、エラーオブジェクトの realm が動くだけのものです。ティア依存 は、同じプログラムでも LLInt/Baseline と DFG/FTL とで挙動が異なることを示します。

WebKit では ShadowRealm は「testable」機能（--useShadowRealm=1、デフォルト無効）であり、F13–F16 が WebKit で緊急事態になっていない唯一の理由がそれです。F1 は通常の realm 間ではフラグ不要で、フラグを立てた瞬間にサンドボックス脱出になります。Bun は ShadowRealm を有効な状態で出荷しているため、最終列の「再現・デフォルト」は実際に踏める状態にあります。それ以外はすべて素の jsc で再現します。

realm の同一性は JSC のどこで入り込むか

役に立つメンタルモデルはこうです——CodeBlock のリンク以前には realm を知るものは何もなく、それ以降のすべては realm を決して忘れてはならない。図は各段階と、それぞれが何を知っているか、そして所見がどこに位置するかを示しています。

Lexer・パーサ・バイトコード：間違えようがない

Source/JavaScriptCore/parser/ と bytecompiler/ は、指定 realm 用の SyntaxError を組み立てる箇所（parser/ParserError.h:92-115）とモジュールレコードの生成を除いて、JSGlobalObject を参照しません。CodeCache（runtime/CodeCache.cpp）のキーは SourceCodeKey——ソース、strict 性、スクリプトモード、derived-context／eval-context 種別、アロー関数コンテキスト、コード生成モードのフラグ——で、どれも realm の状態ではないため、UnlinkedCodeBlock が VM 内の全 realm で共有されるのは正当です。realm 依存の操作は間接的に表現されます。リンク時定数（@Array、@Object、@promiseResolve…）、CodeBlock のグローバルオブジェクトに対する op_resolve_scope／op_get_from_scope、そしてリンク済み CodeBlock に置かれる割り当てプロファイルとインラインキャッシュのメタデータです。キャッシュキーを迂回してコード生成に入り込む realm ごとの入力（パーサが読むグローバル単位の機能トグル、unlinked な executable にキャッシュされたテンプレートオブジェクトや RegExp オブジェクト、UnlinkedFunctionExecutable 上の割り当て Structure）を特に探しましたが、見つかりませんでした。direct eval のキャッシュは CodeBlock ごとであり、eval() は別 realm の eval 関数を正しく間接 eval として扱います（interpreter/Interpreter.cpp:110 が呼び出し側 realm の evalFunction() と比較）。

LLInt と Baseline：realm はコードではなくデータ

LLInt はグローバルオブジェクトを CodeBlock レジスタから読みます。Baseline のコードは 2021 年以降「unlinked」——UnlinkedCodeBlock ごとに一度だけコンパイルされ realm 間で共有される——なので、うっかりでも realm ポインタを埋め込みようがありません。loadGlobalObject() は定数プールを経由し、Math.random の高速パスのようなサンクは実行時に callee から realm を読み（jit/AssemblyHelpers.cpp:900-905）、グローバルオブジェクトを必要とするインラインキャッシュのスタブ（カスタムアクセサ、getter/setter 呼び出し）は所有する StructureStubInfo から取得します。これらのティアが手作業で下す唯一の realm 判断は呼び出しパス上——callee が呼び出し不能／構築不能なときにどの realm の TypeError を投げるか——にあり、F11(a) はそこにあります。

DFG と FTL：globalObjectFor(codeOrigin) と intrinsic の隙間

最適化コードは CodeBlock ごとなので realm ポインタは定数になり、インライン展開によって1つのグラフに複数の realm が日常的に混在します。グラフはこれを m_graph.globalObjectFor(node->origin.semantic) で扱い、ノードが由来するインライン先の関数の realm を返します——JS で書かれたビルトインを含め、インラインされた JS については正しい振る舞いです。隙間は intrinsic のインライン化です。バイトコードパーサが C++ ビルトインの呼び出しを DFG ノードに置き換えるとき、インラインフレームは存在しないので、globalObjectFor() は呼び出し側の realm を返しますが、LLInt/Baseline ならビルトインをそれ自身の realm で実行していたはずです。JSC はこのことを承知しています。calleeMayBeCrossRealm()（dfg/DFGByteCodeParser.cpp:2604-2610）は外部（または不明）の callee のインライン化を拒否して十数個の intrinsic を守り、RegExp 系 intrinsic は明示的な GetGlobalObject(callee) 子ノードを持ちます。F2–F5 は取りこぼされた intrinsic です。覚えておくと役立つ増幅要因があります。NativeExecutable は VM 全体で共有されるため、2つの realm から同じビルトインを見た呼び出し箇所は、CallVariant に関数を持たないが intrinsic は報告するクロージャ呼び出しになります——calleeMayBeCrossRealm() はその場合に保守的に断念しますが、ガードのない intrinsic はすべての呼び出し元に対して呼び出し側 realm の振る舞いをコンパイルします。

ランタイム：「高速かつ観測不能」の中には realm がある

host 関数は callee の realm を受け取り、それはまさに仕様の current realm なので、素直な C++ ビルトインは構造上正しくなります（不正な引数でクロス realm に呼び出した二十数個のビルトインについて投げられたエラーの realm を抜き取り検査したところ、F11 のケースを除きすべて正しかった）。繰り返し現れるバグの形は、(1) 観測可能なプロトコル手順を飛ばしても安全であることをウォッチポイント／Structure で証明し——正しくレシーバの realm を参照して。たとえば RegExpObject::isSymbolMatchFastAndNonObservable() は this->realm() を使う——そのうえで (2) 手元の globalObject、すなわち callee の realm で近道を実行する高速パスです。飛ばされた手順は制御をレシーバの realm へ移していたはずなのに、です。すると結果は誤った realm に実体化し、レシーバの realm の無関係なウォッチポイントが発火した途端に正しい realm へと反転します（F6–F8）。

オブジェクトモデルとヒープ

すべての Structure は自身の realm を記録します。JSObject::realm() はそれであり、JSFunction の realm はスコープチェーンのグローバルオブジェクトで、getFunctionRealm() は束縛関数と Proxy のアンラップを含む仕様上の操作を実装しています（失効した Proxy は正しく例外を投げる）。プロトタイプをキーとする Structure キャッシュは realm ごとで、InternalFunction::createSubclassStructure はキャッシュ済みの new.target 用 Structure を ClassInfo と realm の両方で再検証し、ObjectAllocationProfile は GetFunctionRealm(newTarget) の %Object.prototype% にフォールバックします（通常関数、クラス、Array、Promise、束縛された new.target についてクロス realm の Reflect.construct で確認）。ヒープは VM に1つで realm に無関知です。realm に関係する部分は、マイクロタスクと遅延処理のグローバルオブジェクトへの振り分け（F7／F16 の注記を参照）と、JSGlobalObject::haveABadTime() のクロス realm ヒープ走査で、後者は私が投げた「外部プロトタイプ上の添字アクセサ」テストにすべて耐えました。オブジェクトモデルにおいて意図的に realm 相対になっている唯一の規則が masquerades-as-undefined です（F12）。

最適化 JIT の所見

4件とも jsc --useConcurrentJIT=0 file.js で再現します。再現スクリプトは関数をコールド状態で1回、その後 105 回実行し、両方の答えを報告します。どのケースでも LLInt と Baseline は仕様どおりの答えを返し、DFG/FTL は違う答えを返します。つまり同じプログラムが、生まれて数ミリ秒のうちに挙動を変えるということです。スニペット中の B は createGlobalObject()、realmOf(o) は o のプロトタイプチェーンを辿り、どの realm の Object.prototype に行き着くかを返します。

最近 C++ 化されたこれらの String メソッドには DFG intrinsic があり、その前提条件は呼び出し側の stringSymbol{Match,Search,Split}WatchpointSet（m_graph.isWatchingStringSymbolSplitWatchpointSet(currentCodeOrigin()) など）だけです。callee が realm C の String.prototype.match であるとき——親フレームが子フレームの String メソッドを移植した、あるいはライブラリが uncurry した参照を握っている場合——LLInt/Baseline は C のビルトインを実行し、それは C で RegExpCreate を行い C の RegExp.prototype[@@match] を尊重します。DFG ノードは operationStringMatch/Search/Split(lexicalGlobalObject, …) に下ろされるので、参照も確保も realm A で行われます。realm C での RegExp.prototype[Symbol.match] や [Symbol.search] の上書きは呼び出し元が最適化された時点で呼ばれなくなり、結果の配列は realm を変え、レガシーな RegExp.lastMatch／$1 静的プロパティは誤った realm に書き込まれます。RegExpSplitFast にも別の理由で同じ問題があります。兄弟の RegExpExec／RegExpTest／RegExpMatchFast（addToGraph(GetGlobalObject, callee) を持つ）と違い、グローバルオブジェクトの子ノードなしで生成され、バックエンドが LinkableConstant::globalObject(node) で代用するのです。Fixup でも、RegExp 引数を伴う StringMatch／StringSearch は同様に、ハードコードされた JSConstant(globalObjectFor(origin)) 付きの RegExpMatchFast／RegExpSearch に変換されます。

2つのことが目を引きます。第一に、純粋な C++ のランタイムまたはオブジェクトモデルの所見（F7–F11、F17）は一対一で移ります。Bun の vm コンテキストは完全な意味での realm なので、Promise、バッファ、ジェネレータ、コンストラクタをコンテキスト境界越しに手渡す「サンドボックス」コードは、ウォッチポイント依存の反転を含め、WebKit とまったく同じ挙動を目にします。第二に、JIT の所見は古さに応じて移ります。Bun のスナップショットは PromiseThen intrinsic（F2）と、より古いガードなし intrinsic（F4、F5）を持ちますが、この夏の String intrinsic（F3）は持たず、上流がその後 Object.keys に加えたガードも欠いています——calleeMayBeCrossRealm の一斉適用は、つまみ食いではなく一まとまりとしてバックポートする価値があるということです。

運用上重要なのは ShadowRealm の行です。WebKit ではフラグの背後にある出荷前のバグですが、Bun 1.3.14 では new ShadowRealm() がそのまま動くため、F1、F13、F14、F15 は、ShadowRealm 内のコードがホスト realm の Function コンストラクタを手に入れる（そしてホスト側コードが生の ShadowRealm 側オブジェクトを渡される）ための、独立した、フラグ不要の4通りの経路です。今日 Bun で ShadowRealm を隔離境界として使っている人は、隔離境界を持っていません。node:vm 自体は隔離を約束したことがない（Node のドキュメントもそう明言している）ので、素のコンテキスト間での F1 はそこでは「単なる」仕様逸脱です——V8 も同じことをします——が、Bun の vm コンテキスト内の非 strict モード関数がメイン realm にいる呼び出し元の関数オブジェクトに手が届く、ということは知っておく価値があります。

フロントエンドとリンク

  • パーサ／BytecodeGenerator は JSGlobalObject を取らない。SourceCodeKey はコード生成へのすべての入力を網羅。realm 固有のものは Unlinked* オブジェクトにキャッシュされない。シンボルテーブルは realm ごとに複製。テンプレートオブジェクトは realm ごとの ScriptExecutable にキャッシュ。RegExp リテラルは実行時の realm の Structure で確保。
  • direct eval は callee を呼び出し側 realm の eval と比較する（interpreter/Interpreter.cpp:110）ので、別 realm の eval はその realm での間接 eval として正しく扱われる。direct eval のキャッシュは CodeBlock ごと。

LLInt、Baseline、IC、サンク

  • Baseline のコードにコンパイル時の realm はない：loadGlobalObject()、真偽判定／偽装検査用の LazyBaselineGlobalObject、読み込んだ realm から epoch／var-injection 状態を読むスコープ解決サンク、実行時 realm の Function.prototype[@@hasInstance] と比較する instanceof。
  • ハンドラ IC は CodeBlock ごとの PropertyInlineCache から realm を読む。共有スタブは AccessCase::canBeShared で十分きつくキー付けされ、残る即値はすべての共有者で同一になる。カスタムアクセサとカスタム値は LLInt（runtime/PropertySlot.cpp）、Baseline IC、DFG のいずれでも一貫して保持者の realm を受け取る——DFG は保持者が別 realm のカスタムアクセサのインライン化を拒否する（bytecode/GetByStatus.cpp:358-360、PutByStatus.cpp:267-268）。これはホットな A の関数から B.RegExp.lastMatch を読んで確認した（誤った realm を渡されれば getter は投げるはずだが、一度も投げなかった）。
  • ネイティブ呼び出しトランポリンは host の JSFunction には callee->scope() の realm を、それ以外には InternalFunction::globalObject() を渡す。「関数でない／コンストラクタでない」エラーは LLInt でも呼び出し IC でも呼び出し側の realm で作られる（F11 が唯一の非対称）。
  • iterator_open／iterator_next の高速パスは、取得した @@iterator が字句上の realm の Array.prototype.values などと同一であることを要求するので、外部の iterable はジェネリックに回る。iterable の realm でモンキーパッチされた Array.prototype[Symbol.iterator] や %ArrayIteratorPrototype%.next は、for-of、スプレッド、分割代入、Array.from、new Set/Map、Math.max(...x) によって尊重される——コールドでもホットでも、ティアアップの前後どちらでパッチしても、単相でも realm 混在の呼び出し箇所でも。

DFG/FTL

  • ガード付きの intrinsic：Array/TypedArray の entries/keys/values、slice、splice、concat、Object.keys/getOwnPropertyNames/getOwnPropertySymbols、Map/Set のイテレータ生成と next、文字列イテレータ、%RegExpStringIterator%.next。RegExp.prototype.exec/test/@@match/@@search は GetGlobalObject(callee) を持ち、レシーバを字句上の regExpStructure に固定する。Array/TypedArray コンストラクタと handleConstantFunction の Object／String／RegExp／Map／Set／ArrayBuffer／Symbol は function->realm() を使う。Array.of は this を字句上のコンストラクタと照合する。indexOf/includes/join/sort は字句上の realm の元の配列 Structure に固定するので外部の配列は OSR exit する。
  • バイトコードパーサ内のすべての m_codeBlock->globalObject() は m_inlineStackTop（インライン先）のコードブロックのもの。OSR exit／実体化コードはインラインフレームごとに realm を導出する。StrengthReduction はクロス realm の NewRegExpUntyped の畳み込みを拒否する。ほかにおよそ70個のビルトイン（イテレータ、Object.keys/values/entries、Array.of/from、slice/concat/map/filter/splice/flat、JSON.parse、RegExp の exec/split/matchAll、TypedArray、ボックス化プリミティブ、コンストラクタ）をランタイム担当のサブ監査がコールド／ホットでクロス realm に駆動したが、F2–F5 以外の反転はなかった。

ランタイムとオブジェクトモデル

  • ArraySpeciesCreate はクロス realm の %Array% の例外規定を実装している。TypedArray の species は inSameRealm を検査する。typedArray.buffer はビューの realm に実体化する。Array.prototype.concat は外部 realm の @@isConcatSpreadable を尊重する。JSON の高速 stringifier はプロトタイプの同一性を検査するので外部の Object.prototype.toJSON は尊重される。Object.assign／スプレッドのクローン高速パスは同一 realm・同一プロトタイプを要求する。
  • F2/F7 以外の Promise：Promise.resolve は外部の Promise をラップする（promise->realm() によるコンストラクタ同一性）。all/race/any/allSettled は外部 Promise を thenable ジョブに通す（パッチした外部の then は正しい回数だけ呼ばれる）。外部 Promise の await は仕様どおり2ティック余分にかかり、パッチした then を尊重する。async ジェネレータの結果はジェネレータの realm を使う。
  • GetPrototypeFromConstructor のフォールバック：.prototype がオブジェクトでないクロス realm の new.target による Reflect.construct は、通常関数、クラス、Array、Promise、ジェネレータ関数について new.target の realm の intrinsic を与え、束縛された new.target はターゲットの realm にアンラップされる。割り当てプロファイルのキャッシュはクロス realm の汚染が起きないようにキー付けされている。Reflect.construct(B.Object, [v], ntA) は仕様の「NewTarget が active function でない」分岐に従う。
  • 実体化されたカスタムアクセサ関数（Object.getOwnPropertyDescriptor(B.RegExp, "lastMatch").get）は保持者の realm で作られ、どの realm が尋ねても同一。レガシーな RegExp 静的アクセサはレシーバの realm を読み書きする。Intl のレガシーコンストラクタ用シンボルは realm ごと。Iterator.from は外部イテレータをラップする。不正な引数でクロス realm に呼んだ二十数個のビルトイン（B.Array(-1)、B.JSON.parse("{")、B.BigInt(1.5)、new B.Uint8Array(-1)、B のクラスを new なしで呼ぶ、…）は仕様どおり callee の realm のエラーを投げた——例外は F11 が挙げるもの。
  • クロス realm の「having a bad time」：realm A の Array.prototype に添字アクセサを置くと、そこにチェーンが届く他 realm（後から作られた realm を含む）で作られたオブジェクトと配列は SlowPutArrayStorage になり、インタプリタでもホットな DFG のストアからでも setter を叩いた——上のヒープの注記を参照。

手法と再現手順

この監査は3つを組み合わせました。第一に、JSGlobalObject* が単に受け渡されるのではなく選ばれるあらゆる場所——DFG の intrinsic とアクセサのインライン化、観測可能なプロトコル手順を飛ばす C++ 高速パス、ShadowRealm のマーシャリング、レガシーリフレクション、遅延生成されるラッパ——の読解。一部は私が、一部は並列の5本のサブ監査（DFG/FTL、ランタイム高速パス、ShadowRealm、LLInt/Baseline/IC 共有、オブジェクトモデル/GC）が行い、その候補リストを私が壊しにかかりました。第二に、このチェックアウトの JSCOnly リリースビルドでの差分テスト。同じ操作を同一 realm と外部 realm のオブジェクト（createGlobalObject()）に対して行い、同じ呼び出しをコールド状態と --useConcurrentJIT=0 での 105 回反復後とで実行して、どの realm のプロトタイプ、エラー、realm ごとの状態が関与したかを比較しました。第三に、生き残った各候補を現行の仕様テキストと照合。もっともらしい候補のいくつかはここかシェルで死にました（カスタムアクセサのインライン化、割り当てプロファイルの汚染、イテレータの高速パス、JSON、配列と TypedArray の species）——それらは黙って捨てず前節に記録してあります。

上のすべての所見は PASS／FAIL 行を出力するスクリプトに裏付けられており、引用した出力はそのままの写しです。スクリプトはこの報告書と並べて監査ブランチ（claude/javascriptcore-realm-bugs-njnwvw の realm-audit/repros/）にコミットしてあり、素のシェルで動きます。
